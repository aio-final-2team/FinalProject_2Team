# 피드백 처리 방법

강사님·멘토님·팀원 피드백을 한 곳에 모으고, 누가 무엇을 할지 자동으로 나누는 방법입니다. 피드백이 여러 곳에서 계속 들어오고 기획서·WBS·보드를 그때마다 고쳐야 해서, 피드백이 들어오는 곳과 문서를 고치는 사람을 하나로 정했습니다.

정리하면 이렇습니다. 피드백을 디스코드 `#피드백`에 올리면 봇이 번호를 매기고 담당자를 멘션합니다. 담당자는 맞는 위치에서 작업하고, 같은 PR에 자기 폴더 메모를 같이 올립니다. 지혜님은 메모 중 기획서·WBS에 반영할 것을 모아 반영합니다.

이 문서를 AI에게 그대로 넣고 일을 시켜도 됩니다. 그때 AI가 지킬 규칙은 [7. AI에게 맡길 때](#7-ai에게-맡길-때)에 있습니다.

## 1. 전체 흐름

| 단계 | 누가 | 무엇을 |
| --- | --- | --- |
| 1 | 피드백을 받은 사람 | `#피드백` 채널에 올립니다. 첫 줄에 누가 준 피드백인지 적습니다. |
| 2 | 봇(`태웅's 클로드`) | 1분 안에 그 글에 스레드를 열고, 번호를 매기고, 할 일을 항목별로 나눠 담당자를 멘션합니다. |
| 3 | 담당자 | 맞는 위치(코드·설계서 등)에서 작업하고, 같은 PR에 자기 폴더 메모(한 일·기획서·WBS 반영)를 같이 올립니다. |
| 4 | 지혜님 | 메모의 '기획서·WBS 반영' 칸을 모아 기획서·WBS·GitHub Projects에 반영합니다. |
| 5 | 누구나 | 작업하다 생긴 문제도 다시 `#피드백`에 올립니다. 그러면 1단계부터 같은 흐름으로 돕니다. |

기획서·WBS 원본(`Docs/Step1`)은 지혜님만 고칩니다. 다른 사람은 바꿀 문장을 메모에 적기 때문에 기획서·WBS를 두고 PR끼리 겹치지 않습니다. 메모 폴더는 사람마다 따로라서, 모아 보면 누가 어떤 피드백을 어떻게 반영했는지 기록이 됩니다.

## 2. 피드백 올리기

- 채널에 바로 올립니다. 스레드 안에 쓴 글은 봇이 읽지 않습니다.
- 첫 줄에 출처(강사님·멘토님·팀원 이름)를 적습니다. 나머지는 자유롭게 써도 됩니다. 번호가 매겨져 있으면 그 번호대로 나눕니다.
- 사진(캡처)도 읽습니다. 글이 길면 `.md`나 `.txt` 파일(50KB까지)로 첨부해도 됩니다. 그 밖의 파일은 읽지 못합니다.
- 이미 끝낸 항목은 "6번은 이미 했어요"처럼 적어 주면 할 일에서 빼고 따로 표시합니다.
- 인사, "확인했습니다" 같은 답장, 일정 공지에는 반응하지 않습니다. 채널에서 짧게 이야기해도 괜찮습니다.
- 다른 봇이나 자동화(웹훅)가 올린 글도 똑같이 처리합니다. 봇이 스스로 단 글에는 반응하지 않습니다.

예시:

```
강사님 일일 피드백 11/17
1. 화면·API·도구·평가 문항의 이름과 형식을 맞춰 주세요. …
2. 기획서·WBS의 2차 보완을 실제 수정본으로 마무리해 주세요. …
6. 모델 선택은 정확도·시간·비용을 함께 보고 결정해 주세요. …
6번은 이미 했어요.
```

## 3. 봇이 다는 글 읽기

```
FB-001 · 11/18 · 출처: 강사님 · 올린 분: 태웅

FB-001-1 [작업] 도구·API·평가 문항 이름과 형식을 계약표 기준으로 맞추기
→ @태웅 · WBS T10 입출력 계약 합의, T13 API 설계 문서

FB-001-2 [문서] 기획서·WBS 2차 보완 수정본 마무리하기
→ @지혜 · 기획서 표지·9 일정과 역할, WBS T02

이미 했다고 적힌 것: 6번
참고: 원문만으로는 애매한 점
```

- **번호**: `FB-001`은 피드백 한 건, `FB-001-2`는 그 안의 두 번째 할 일입니다. 번호는 계속 이어집니다.
- **`[문서]` / `[작업]`**: 메모의 '기획서·WBS 반영' 칸을 채워야 하는지 알려 줍니다. 기획서·WBS 문구도 바꿔야 하면 `[문서]`, 작업만 하면 끝나는 일이면 `[작업]`입니다. 어느 쪽이든 작업과 메모는 똑같이 올립니다.
  - `[문서]` 예: 기획서 위험 표에 행 추가, 결정 기록 칸 채우기, WBS 일정·담당 바꾸기
  - `[작업]` 예: API·도구 이름 맞추기, DB 시험 기록 남기기, `Docs/Step2` 설계서 고치기, 코드 수정
- **`[새 작업]`**: WBS에 없는 일이고, 새 기능·새 산출물처럼 하루 이상 걸려 일정을 따로 잡아야 하는 일입니다. 고칠 곳에 "WBS에 없음"이 붙고, 봇이 지혜님 몫 항목("FB-002-1을 WBS·보드에 새 작업으로 추가하기")을 같이 답니다. 담당자는 지혜님 반영을 기다리지 않고 바로 작업합니다. WBS에 없더라도 하루 안에 끝나는 수정·보완은 `[문서]`나 `[작업]`입니다.
- **담당**: 봇이 관련 WBS 작업의 담당자로 정합니다. 없으면 역할로 정하고, 그래도 애매하면 지혜님으로 정한 뒤 "(담당 확인 필요)"를 붙입니다.
- **고칠 곳**: `develop` 브랜치의 `Docs/Step1/기획서.md`와 `Docs/Step1/WBS.md`에서 절 번호, 요구사항 ID(FR·NFR·AC), WBS 작업 ID를 찾아 적습니다.
- **참고**: 원문만으로 판단하기 어려운 점입니다. 담당자가 확인하면 됩니다.

## 4. 담당자가 할 일

항목 하나마다 PR 하나에 두 가지를 같이 올립니다. 평소처럼 자기 브랜치에서 `develop`으로 올립니다.

1. **작업**: 그 일이 원래 있어야 할 위치에서 합니다. 코드면 코드 폴더, 설계서면 `Docs/Step2` 같은 식입니다. 기획서·WBS 원본(`Docs/Step1`)은 고치지 않습니다.
2. **메모**: 자기 폴더에 항목 번호로 `.md` 파일을 만듭니다. 예: `Docs/Feedback/taewoong/FB-001-3.md`

| 폴더 | 담당 |
| --- | --- |
| `Docs/Feedback/jihye` | 박지혜 |
| `Docs/Feedback/taewoong` | 문태웅 |
| `Docs/Feedback/youngmin` | 손영민 |
| `Docs/Feedback/sungju` | 차성주 |
| `Docs/Feedback/inhye` | 김인혜 |

### 메모 양식

`[작업]` 항목 예시(기획서·WBS는 그대로):

```
피드백: FB-001-3
한 일: Docs/Step2/DB_스키마_설계서.md 상태 이름을 API 설계와 맞추고 DB 제약 시험 결과를 추가함 (이 PR)
기획서·WBS 반영: 없음
```

`[문서]` 항목 예시(기획서·WBS 문구도 바꿔야 함):

```
피드백: FB-001-5
한 일: 서버 비용 근거 정리, 매주 월요일 #저장용 비용 자동 보고 시작
기획서·WBS 반영:
- 고칠 곳: 기획서 11장 결정 기록 표 '배포 서버' 행, 마지막 칸
- 바꾸기 전: AWS 구성·비용·비밀값·백업·복구와 웹 배포 URL의 확인 근거를 기록
- 바꾼 후: 비용 근거(11/18 기준). EC2 t3.large $0.104/시간 × 1,152시간 ≈ $120, …
```

`[새 작업]` 항목 예시(WBS에 새 작업으로 들어가야 함):

```
피드백: FB-002-1
한 일: 알림 내역 API 초안 추가 (이 PR)
기획서·WBS 반영:
- 새 작업: 알림 내역 화면·API 만들기 / 11/19~11/21 / 선행 T26
```

- "한 일"에는 어디를 어떻게 바꿨는지 적습니다. 문서만 바꾸면 되는 일이라 따로 한 작업이 없으면 `없음`이라고 씁니다.
- "바꾸기 전"에는 지금 기획서·WBS에 적힌 문장을 그대로 복사하고, "바꾼 후"에는 대신 들어갈 문장을 씁니다. 새 행을 추가하는 거면 "바꾸기 전"에 `(없음)`이라고 씁니다.
- 고칠 곳이 여러 군데면 `- 고칠 곳` 묶음을 여러 개 씁니다.

### 담당이 잘못 잡혔을 때

스레드에 맞는 사람을 멘션해서 넘깁니다. 봇은 같은 글을 다시 나누지 않으니, 넘겨받은 사람이 그대로 처리하면 됩니다.

## 5. 지혜님이 할 일

PR을 확인해 머지하고, 메모의 '기획서·WBS 반영' 칸에 적힌 것을 기획서·WBS·GitHub Projects에 반영합니다. 반영하지 않기로 했으면 PR에 이유를 남깁니다.

`[새 작업]`이 나오면 봇이 지혜님 몫 항목을 따로 답니다. 담당자 메모의 `- 새 작업:` 줄대로 WBS 작업 계획표에 새 작업(T 번호)을 넣고, 보드에 카드를 추가합니다. 이 일도 다른 항목처럼 작업(WBS 수정)과 자기 폴더 메모를 한 PR로 올립니다.

## 6. 봇이 반응하지 않을 때

- 1분이 지나도 스레드가 생기지 않으면, 채널에 바로 올렸는지(스레드 안이 아닌지) 확인합니다. 인사나 공지처럼 보이는 글이면 피드백으로 보지 않습니다.
- 봇은 1분마다 다시 시도합니다. 세 번 시도해도 나누지 못하면 봇이 "자동으로 못 나눴어요. 지혜님이 직접 나눠 주세요."라고 남깁니다.
- 그 밖의 문제는 태웅에게 알려 주세요.

## 7. AI에게 맡길 때

이 문서와 함께 **봇 스레드의 내 항목 줄**과 **피드백 원문**을 붙여 넣고 이렇게 시키면 됩니다.

- "FB-001-3이 내 `[작업]` 항목이야. 이 규칙대로 작업하고 메모까지 써줘."
- "FB-003-1이 내 `[새 작업]` 항목이야. 작업하고, 메모에 새 작업 줄까지 써줘."
- "FB-002-1이 내 `[문서]` 항목이야. 작업할 게 있으면 하고, 메모의 기획서·WBS 반영 칸까지 써줘. 강사님 원문은 이거야: …"

AI가 지킬 규칙:

1. `Docs/Step1`의 기획서·WBS 원본 파일은 고치지 않는다. 바꿀 문장은 메모로만 쓴다.
2. 작업은 그 일이 원래 있어야 할 위치(코드 폴더, `Docs/Step2` 등)에서 한다.
3. 같은 PR에 메모 `Docs/Feedback/<담당자 폴더>/<항목 번호>.md`를 4절 양식(피드백·한 일·기획서·WBS 반영)으로 만든다. 담당자 폴더는 4절 표에서 찾는다. "바꾸기 전"에는 `develop` 브랜치의 `Docs/Step1/기획서.md` 또는 `Docs/Step1/WBS.md`에서 해당 문장을 그대로 복사해 적는다. `[새 작업]` 항목이면 기획서·WBS 반영 칸에 `- 새 작업: 작업명 / 기간 / 선행` 한 줄을 쓴다.
4. PR은 자기 브랜치에서 `develop`으로 올린다. `main`에는 올리지 않는다.
5. 다른 사람 폴더의 파일은 건드리지 않는다.
6. 비밀값(API 키·비밀번호)이나 실제 아이(원아) 정보는 넣지 않는다.
7. "바꾼 후"에 넣을 숫자·사실이 원문이나 문서에 없으면 지어내지 말고 사용자에게 묻는다.
8. PR은 사용자가 내용을 확인한 뒤에 올린다.
