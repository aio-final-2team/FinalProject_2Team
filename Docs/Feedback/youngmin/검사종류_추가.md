# 알림장 검사 종류 분리: `memo_missing`·`request_unanswered`

2026-11-27 · 영민 담당 에이전트 코드 작업 · 기준 `origin/develop` `d8a9d219`

## 바뀐 판정

| `open_checks.kind` | 의미 | 코드 판정 | 교사 화면 제안 |
| --- | --- | --- | --- |
| `memo_missing` | 비어 있지 않은 아이 관찰 메모가 있는데 `child` 줄이 없음 | 다른 아이·민감·날짜·결석 등 `child` 확인이 이미 있으면 그 판정을 보존. 다른 확인이 없으면 `memo_missing`을 만들고 자료 AI에 최대 2회 재작성 요청. 끝까지 없으면 `memo_missing`과 `return_limit`을 열어 둠. 메모 원문은 `sentence`에 넣지 않음 | “아이 관찰 메모가 빠졌어요” / “메모 보고 한 줄 쓰기” |
| `request_unanswered` | 문의 줄은 있으나 메모에 답할 내용이 없어 `answered:false` | 기존 `sensitive` 대신 해당 요청 `request_id`와 `item_key: inquiry`, 문의 줄 `sentence`를 담아 선생님 확인으로 넘김. 자동 재작성 대상은 아님 | “보호자 요청에 답이 필요해요” / “답 한 줄 쓰기” |

`sensitive`는 실제 다침·열·투약·갈등·가정사 등 선생님이 꼭 볼 내용에 남긴다. `not_in_memo`, `request_missed`와 기존 안전 확인의 의미는 바꾸지 않았다. `agents/prompts/checker.md`는 #389 머지 뒤 별도 수정 대상이라 이 브랜치에서는 건드리지 않았다. 따라서 현재 검사 모델 자체는 새 종류를 내지 않고, 두 종류는 에이전트 코드가 낸다.

## 서버·화면 계약 및 머지 순서

태웅: `apps/api/app/api/schemas/views.py`의 `OpenCheck.kind`에 두 값을 추가해야 한다. 지금 `apps/api/app/modules/daily_notes/runner.py`는 모르는 종류를 `check_failed`로 바꾼다. `memo_missing`의 `item_key`는 `child`, `sentence`는 `null`, `request_id`는 없음. `request_unanswered`의 `item_key`는 현재 자료 AI가 쓰는 `inquiry`, `request_id`는 해당 UUID, `sentence`는 문의 줄이다. 서버 `NoteLine`/`OpenCheck`의 `item_key` 허용 범위와 문의 줄 호환성도 확인해야 한다.

성주: `apps/web/src/domain/notes.ts`의 `CheckKind`와 `CHECK_KIND`, `features/notes/NoteDetail.tsx`의 카드 동작을 갱신한다. `memo_missing`은 메모를 읽고 `child` 줄을 쓰게 하고, `request_unanswered`는 요청 줄 편집으로 이동해 답을 저장할 때 확인을 해소한다. 기존 `sensitive`의 “이 문장 빼기”를 두 경우에 재사용하면 의미가 틀린다. 웹 `ItemKey`에도 현재 `inquiry`가 없어 문의 줄 계약을 태웅과 맞춰야 한다.

**서버 새 종류 허용 PR → 화면 새 카드 PR → 이 에이전트 브랜치 머지** 순서로 켠다. 이 브랜치를 먼저 머지하면 초안의 새 종류가 서버에서 `check_failed`로 바뀐다. #389가 머지되면 그 위에서 `checker.md`의 설명·종류를 별도 정리한다.

## 평가 기대값과 비용

`tools/eval_daily_note.py`의 정상 메모 비표시 확인 집합에 `memo_missing`을 넣었다. 요청 채점기는 기대 `teacher_check`와 실제 `open_checks.kind`를 동적으로 비교하므로 `request_unanswered` 자체는 추가 허용표 없이 검사할 수 있다. 새 종류의 채점 동작은 단위 시험으로 확인했다. 실제 모델 호출은 하지 않았고, `--model echo` 실행은 입력·출력 형식 점검용이다. Echo는 메모를 그대로 옮기고 검사 결과를 비워 두므로 의미 품질의 근거가 아니다.

기존 `sensitive` 기대값 재검토 목록(이번에는 데이터 변경 없음): `GR-20`은 메모에 친구 이야기가 없는 `memo_silent` 문의라 답이 없으면 `request_unanswered`가 맞다. `GR-14`도 관찰 메모에는 기침 답이 없으므로 문의 답 없음은 새 종류로 표시해야 하지만, 건강 내용 자체의 `sensitive` 확인과 병존 가능하다. `GR-18`은 친구 갈등 메모의 실제 `sensitive`가 남아야 하므로 단순 치환하지 않는다. `ND-06/07/08/09/11/12/13/20` 등 기존 `sensitive` 기대는 실제 안전·민감 메모이므로 유지한다. 예전 모델 결과의 누락 때문에 `sensitive`가 대신 붙은 사례는 원자료를 확인한 뒤 별도 평가 개정에서 고른다.
