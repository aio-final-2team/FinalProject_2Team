# 알림장 코드 판정 범위 조정

2026-11-27 · 영민 담당. 11/27 팀 결정(#일반 17:38 태웅·17:39 지혜, #409 태웅 댓글)에 따라 새 `open_checks.kind`와 고정 카드 제목·버튼 제안은 보류한다. 검사 AI가 문제와 행동을 자기 말로 쓰는 방향을 정한 뒤 계약을 다시 논의한다. 이 브랜치의 후속 커밋은 에이전트 코드와 모델 없는 평가만 조정한다.

## 이번에 하는 일

- `child` 줄이 없고 관찰 메모가 비어 있지 않으며, 검사 결과에 `sensitive`·`other_child`·`date_check`·`absent`처럼 누락 사유가 있는 판정도 없다면, `memo_left_out`을 **자료 AI에게만 전달하는 내부 재작성 신호**로 쓴다. 최대 2회 다시 쓰게 한다. `not_in_memo`는 실제 줄이 없다는 문제를 대신하지 못하므로 재작성을 막지 않는다.
- 재작성 뒤에도 줄이 없으면 기존 허용 종류 `return_limit`만 `open_checks`에 남기고 사람 확인으로 넘긴다. `return_limit`은 “AI가 두 번 고쳐도 남은 문제가 있음”이라는 실제 상황에 맞는다. 내부 신호는 `open_checks`에 넣지 않는다. `check_failed`·`draft_failed` 경로도 기존 종류만 사용한다.
- 문의의 `answered:false` 또는 메모 줄과 중복된 문의 문장은 코드에서 `sensitive`로 바꾸지 않는다. 요청 줄은 유지한다. 검사 AI가 내용 자체를 독립적으로 `sensitive`라고 판정한 경우의 확인은 보존한다. 답 없음 전용 표시·행동은 새 방향이 정해질 때까지 만들지 않는다.

## 계약과 채점

외부 `open_checks.kind`는 기존 9종(`not_in_memo`, `sensitive`, `other_child`, `date_check`, `absent`, `draft_failed`, `check_failed`, `request_missed`, `return_limit`)만 낸다. 서버 `views.py`, 화면 `notes.ts`, `checker.md`는 수정하지 않는다. 서버 허용값 추가나 고정 화면 문구도 이번 변경에 필요 없다. `answered` 출력 형식은 남아 있지만 이 코드 판정에서는 쓰지 않는다.

채점기 `tools/eval_daily_note.py`의 종류 집합은 기존 5종으로 되돌리고, 일반 관찰 메모에 `child` 줄이 없으며 안전·날짜·결석 등 누락 사유도 없으면 `return_limit`이 붙어 있더라도 실패로 센다. 원자료의 `must_include` 의미 검사는 여전히 사람 판정이다. `guardian_requests.json`의 기존 `teacher_check: sensitive` 중 GR-20은 답 없음 자체만으로 기대할 수 없고, GR-14는 건강 내용의 별도 민감 판정 여부를 구분해야 한다. 이 두 문항의 기대값 개정은 새 검사 방향과 함께 논의한다. 이번에는 평가 데이터 자체를 바꾸지 않는다.

“최종에도 빠지면 확인 표시 없이 둔다”는 선택은 하지 않았다. 현재 허용 종류 중 `return_limit`이 정확히 재작성 실패를 뜻하고, 표시 없이 두면 알림장 발송 전 사람 확인이 빠질 수 있기 때문이다. 별도 `memo_missing` 종류를 만들지 않아도 실패 사실을 알릴 수 있다는 것이 판단 근거다.

## 검증

- 실제 모델·팀 서버·공용 DB 호출 없음. `--model echo`는 형식 확인용이며 의미 성능의 근거로 쓰지 않는다.
- 대상 단위 시험 40개, 전체 단위 시험 481개 통과(맥 전용 셸 도구 차이 6개 제외). 변경 Python 파일 Ruff와 `git diff --check` 통과.
- `tools/eval_daily_note.py --model echo`: 메모 7/20, 요청 13/20. Echo는 메모를 그대로 옮기고 검사 결과를 비워 두므로 형식 기준선이며 품질 판정에 쓰지 않는다.
