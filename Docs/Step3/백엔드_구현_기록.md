# 백엔드 구현 기록

2026-11-21 기준이에요. 모의 API와 같은 계약을 쓰는 PostgreSQL 백엔드를 만들었어요.
업무 API 37개 중 DB 구현은 35개이고, 자료 업로드·상세 두 개는 501로 남아요.
알림장 → 문의·민원 → 상담·기억 → 워커·알림·CI 순서로 연결했어요.
투약·귀가와 상담 지연 입력은 **팀 확인 전 초안**이에요.
이 문서 기준 코드의 구현 범위와 시험 결과를 정리했어요.

별빛반은 원래 시드의 만 4세 반·teacher01을 유지해요. PR #262의 가상 아이 18명을 더해

보호자 요청은 기존 2개와 PR #269의 20개, 총 22개예요. 요청이 있는 C4 아이의 보호자 계정도 연결했어요.
시드는 다시 실행해도 기존 행을 덮어쓰지 않아요. 날짜 갱신 옵션은 fixture 날짜 간격을 유지하며
요청과 최초 보호자 메시지를 함께 옮겨요. 절차는 API README의 데모 절을 봐 주세요.

## 3. 결정과 이유

| 결정 | 이유·현재 동작 |
| --- | --- |
| `DATA_BACKEND=mock\|db`, 기본 mock | 프론트의 모의 계약을 유지하면서 영역별 DB 구현을 연결해요. DB 주소는 앱 전용 DATABASE_URL로 받아요 |
| SQLAlchemy 2.0 Core·동기 psycopg 3 | SQL과 트랜잭션을 코드에서 직접 설명할 수 있게 해요. 공통 저장소 추상화는 더하지 않았어요 |
| JWT에 반 소속을 넣지 않음 | 매 요청 현재 DB 관계를 읽어 배정·보호자 관계 변경을 반영해요. 없는/비활성 계정도 더미 argon2 검증을 한 번 해요 |
| DB JWT_SECRET 기동 검사 | 기본값·예시 값·32바이트 미만 키는 DB 앱을 시작하지 않아요. mock의 개발용 기본값은 허용해요 |
| 상태·이력·승인·알림을 같은 트랜잭션에 저장 | 결정만 저장되고 회신·알림이 빠지는 부분 성공을 막아요. 범위 거부 이력만 별도로 커밋해 404 뒤에도 남겨요 |
| 요청 → 카드 UUID 순서의 행 잠금·version·승인 유니크 | 같은 판 중복 결정과 교착을 줄여요. 카드 결정은 FOR NO KEY UPDATE를 쓰고 충돌은 기존 409로 답해요 |
| 상담 담임 → 상담실 자문 잠금·배제 제약 | 서로 다른 카드의 동시 예약도 직렬화해요. 예약 충돌·교착은 SLOT_TAKEN으로 바꿔요 |
| 작성기·요청 에이전트 입구를 설정으로 선택 | API가 에이전트 내부에 묶이지 않게 해요. 요청 입구는 카드와 요청 상태를 한 트랜잭션에서 바꿔야 해요 |
| 알림장 실행 판에 입력 행 xmin 사용 | 재생성 전 작업의 늦은 성공·실패가 새 결과를 덮지 못하게 해요. 저장 직전 수정·확인 여부도 다시 검사해요 |
| JSON으로 왕복할 수 있는 작성기 입력 | UUID 문자열·ISO 날짜와 아이별 메모·당일 보호자 요청·식단으로 입구 계약을 고정해요 |
| 이름 가림·개인 기억 범위 | 출처 반의 아이 이름만 낱말·조사 경계에서 가려요. 반이 없으면 기관 전체를 보고, 삭제 시 본문·structured도 비워요 |
| 앱 안 알림·dedupe_key·발송 잠금 | 외부 발송 없이 상태 전이를 검증해요. 총 3회 시도·60/120초 재시도 후 failed, 최초 노출·읽음 시각은 유지해요 |

알림장 입력은 queued → running → succeeded 또는 failed예요. 기본 작성기는 메모를 그대로 옮기는
대역이고, `DAILY_NOTE_WRITER=graph`일 때 실제 그래프를 골라요. 아이 결과 하나가 없거나 잘못되면
그 아이만 draft_failed, 작성기 전체 예외·시간 초과면 입력 전체가 failed예요.
writer 제한은 기본 300초예요. 실제 그래프 연결 시험에는 가짜 writer·checker를 넣어요.

`RUN_IN=api`는 FastAPI BackgroundTasks, `RUN_IN=worker`는 커밋 뒤 Celery에 ID만 보내요.
worker는 notes·default 큐를 기본 threads 4개로 읽어요. Beat는 5분마다 누락 카드·멈춘 초안,
1분마다 발송·상담 알림을 점검해요. 요청은 첫 점검에서 한 번 재전달하고 5분이 더 지나도
카드가 없을 때 인계해요. 투약·귀가는 사람 확인 흐름이라 이 점검에서 빼요.
worker의 멈춘 초안 기준은 작성기 제한 + 60초예요. 지금은 API·worker·Beat 각각 하나가 전제예요.

## 4. DDL과 마이그레이션

0001은 v0.7 적용본을 유지해요. 이후 변경은 새 revision으로만 쌓았어요.

| Revision | 변경 |
| --- | --- |
| 0001 | 초기 표·뷰·트리거·제약 |
| 0002 | 아이별 메모 JSON 배열·CHECK |
| 0003 | 마지막 AI 초안·알림장 이력 FK·이력 네 종류 |
| 0004 | 발송한 민원 회신의 받은함 분류 |
| 0005 | 알림 next_attempt_at |
| 0006 | 요청 재전달 agent_requeued 이력 |
| 0007 | 상담 예상 종료 시각·종료/대체 시간 알림·이력 |
| 0008 | 투약·귀가 접수/확인 알림 |
| 0009 | 상담 예상 종료의 당일·3시간 상한 CHECK |

head는 0009이고 설계 DDL v0.15와 대조해요. 기대 카탈로그는 표 27개·뷰 2개·트리거 2개·
FK 58개·컬럼 271개예요. Alembic 관리 표·확장 객체는 제외해요.
시험에서 base까지 내렸다 올린 스키마와 최신 설계 DDL을 각각 적용한 스키마를
`pg_dump --schema-only`로 비교해요. 무작위 psql 보호 키만 비교에서 빼요.
데이터가 있는 이전 revision의 보존·backfill·제약·되돌리기도 시험해요.

## 5. 최종 시험 환경과 실행

저장소 루트의 `.venv`를 사용했어요. 환경은 Linux x86_64·Python 3.12.3,
pytest 9.2.0·FastAPI 0.163.2·SQLAlchemy 2.0.58·psycopg 3.3.9·Alembic 1.20.1·
argon2-cffi 25.1.0·Celery 5.7.0이에요. Docker 29.1.3·Compose 2.40.3에서
`pgvector/pgvector:pg16` 임시 DB를 썼어요. 패키지 버전은 이번 검증 환경의 값이에요.

mock은 DATA_BACKEND=mock·RUN_IN=api로 두고 TEST_DATABASE_URL 없이 실행해요.
DB 시험은 아래 도구가 자기 전용 DB·임의 호스트 포트·시험용 JWT 키를 만들어요.

```sh
PATH="$PWD/.venv/bin:$PATH" python -m pytest -q
tools/test_db.sh
```

두 명령은 한 번에 하나씩 실행했어요. 첫 명령은 DB가 필요한 경우 skip하고,
두 번째는 DB 통합 시험 뒤 공통 HTTP 시험을 mock·DB로 각각 실행해요.
제품 DB·기본 5432 포트는 쓰지 않아요. 스크립트는 만든 컨테이너만 삭제해요.

| 검사 | 결과 | pytest 실행 시간 | 종료 코드 |
| --- | --- | --- | --- |
| mock 전체 | 535 passed, 558 skipped | 67.26초 | 0 |
| DB 통합 전체 | 271 passed | 230.89초 | 0 |
| 공통 HTTP 전체(mock·DB) | 574 passed | 316.73초 | 0 |

ruff 기본 검사도 통과했어요. 임시 DB 컨테이너가 삭제된 것도 다시 확인했어요.

skip은 통과 수에 넣지 않아요. 공통 HTTP 결과는 같은 사례를 두 모드로 실행한 수라서
mock 전체와 더해 고유 시험 수로 계산하지 않아요. 동시 결정·예약·재확인, 기관/반 경계,
마이그레이션, 작성기 실패·복구, 발송 재시도도 기존 전체 시험에 포함돼요.
이번 사실 대조에서는 서버 Compose의 기본값·이미지 선택 조합을 보강했어요.
업무 API 시험은 기존 그대로예요.

OpenAPI는 mock·DB에서 생성한 스키마와 저장 YAML이 같고, 다시 직렬화한 바이트도 같아요.
T13의 업무 엔드포인트 37개와 health 1개, 총 38개 연산·36개 경로를 확인했어요.
요청·카드 SSE 두 경로의 text/event-stream도 확인했어요. 생성물은 바뀌지 않았어요.
이는 스키마 대조 결과예요. 실제 DB 미구현 두 경로까지 동작한다는 뜻은 아니에요.

## 6. 남은 것과 문서 사이 차이

- DB의 `POST /documents`·`GET /documents/{document_id}`는 인증·역할 검사 뒤 501이에요.
  자료별 기관·반 범위 검사는 아직 연결하지 않았어요. 자료 수집·조각·임베딩·충돌 검사는 후속이에요.
- T46·T48의 추가 계약은 팀 확인이 필요해요. 상담 실제 종료 입력·화면·예약 변경/취소와
  투약·귀가의 구조화 값 변경 경로는 후속이에요. 보호자 새 글은 원문을 보존하고 재확인을 요구해요.
- 요청 분류·회신은 대역이에요. 실제 문의 에이전트·기억 AI의 말투/규칙 추출·근거 품질과
  평가 문항 결과는 이 시험으로 증명하지 않았어요. 알림장 실제 모델 호출도 이번에는 하지 않았어요.
- API·worker·Beat 각각 하나와 공유 스레드 풀이 전제예요. 긴 초안이 모든 스레드를 차지하면
  다른 일이 늦어질 수 있어요. 작성기 시간 초과도 실행 중 스레드·모델 호출을 강제 취소하지 못해요.
- 같은 날 반을 옮긴 아이는 `(child_id, note_date)` 유니크 때문에 묶음이 실패할 수 있어요.
  아이가 없는 반 발송은 sent_count=0이고 묶음 카드는 pending으로 남아요.
- 0003 이전 ai_original은 당시 content로 채웠어요. 실제 원본과 다른 행은 학습 전 검토가 필요해요.
  모의 묶음 카드 타임라인에는 아이별 발송 이력이 표시되지 않을 수 있어요.
- OpenAPI의 info 설명은 mock·DB 두 모드를 안내해요. DB 지원 범위는 API README 진행표를 봐요.
  기존 배포 문서의 워커 도입 전 안내는 T66 초안·현재 Compose와 함께 확인해야 해요.
- CI의 공통 HTTP 목록은 로컬 `tools/test_db.sh`와 같아요. 상담 알림·투약·귀가도 두 모드로 검사해요.
  PR #286·#287에서 mock·PostgreSQL 시험과 API·웹 이미지 빌드 네 작업이 모두 통과했어요.

## 7. [제안] 필수 동의와 화면에서 이어 받을 것

같은 요청을 다시 보내도 최초 시각·응답을 유지하고 이력은 한 줄만 남겨요.

화면은 다음 세 API를 이어 받으면 돼요.

| API | 화면이 할 일 |
| --- | --- |
| GET `/api/v1/me` | user.consents_complete가 false면 동의 화면으로 보내요. 로그인 응답에도 같은 값이 있어요. |
| GET `/api/v1/consents` | 현재 terms_version과 내 역할의 항목·문구·agreed_at을 보여 줘요. |

받으면 동의 화면으로 보내요. 기존 권한 검사가 먼저이고, GET과 나머지 동작은 계속 이용해요.

아이별 연결 보호자 수·완료 수를 보여 주면 돼요. 한 명 이상 완료하면 아이의 complete가 true예요.
화면 코드는 이번에 바꾸지 않았어요. 가입·탈퇴·얼굴 특징정보 저장·데이터 삭제는 범위 밖이에요.

### 8.4 알려진 한계

- 문의 답변 AI는 같은 질문에도 가끔 "근거 없음"으로 답해 담임 확인 카드로 넘겨요. 자료가 없는 게 아니라 모델이 흔들리는 경우예요(#352에서 줄였지만 남아 있어요).
- 서비스가 할 수 없는 질문을 알아보는 첫 규칙은 "우리 아이·우리 애·저희 아이"만 봐요. "제 아이·딸·아들" 같은 표현은 감독 AI가 걸러요. 감독 AI를 끄면 주제 분류에 걸릴 때만 담임에게 가요.
- 협업 그래프를 켜면 자료끼리 충돌할 때 근거와 충돌 표시가 사라져요(이슈 #349).
- CI의 DB 시험이 7분 넘게 걸려요. DB 시험과 공용 HTTP 시험을 차례로 돌려서예요.
