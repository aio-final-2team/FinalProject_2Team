# 팀 작업 규칙

## 브랜치

- `main`은 제출·발표용 브랜치입니다. `develop`에서 `main`으로 PR을 만들고 팀장이 합칩니다. 팀장이 부재 중이면 부팀장이 맡습니다.
- `develop`은 통합·서버 배포용 브랜치입니다. 작업 브랜치의 PR로만 변경합니다.
- WBS 작업 하나마다 최신 `develop`에서 새 브랜치를 만듭니다. 이름은 `<이름>-<T번호>`로 합니다. 예: `ju-t04`.
- PR이 합쳐지면 GitHub가 작업 브랜치를 삭제합니다. 진행 중인 브랜치는 매일 최신 `develop`을 받아 이어서 작업합니다.

## 커밋

- 커밋 메시지는 `종류: 내용` 형식으로 씁니다.
- 종류는 `feat`(기능), `fix`(버그), `docs`(문서), `test`(테스트), `chore`(설정·정리) 중 하나를 씁니다.

## PR과 리뷰

- 작업 PR의 대상은 `develop`입니다. 제목은 `[T번호] 작업 이름`으로 씁니다.
- 본문은 PR 템플릿을 사용하고 `Closes #이슈번호`, 변경 내용, 확인 방법, 남은 문제를 기록합니다.
- WBS 검토 칸의 담당자 1명이 승인하고 필수 CI가 통과하면 팀장이 합칩니다. 팀장이 부재 중이면 부팀장이 맡습니다.
- `contracts/` 변경은 다섯 명 모두 확인한 뒤 합칩니다.
- 하루 작업 단위로 작게 자주 PR을 올립니다. 하루 이상 걸리는 작업은 Draft PR로 먼저 공유할 수 있습니다.
- 팀장은 PR을 몇 개 합칠 때마다 `#일반`에 “develop 받아서 진행해 주세요”와 합친 PR 목록을 알립니다. 각자는 진행 중인 브랜치에서 `git pull origin develop`을 실행합니다.

## 제출 문서

- `Docs/StepN` 문서도 `develop`에 PR로 반영합니다. `main`에 직접 올리지 않습니다.
- 제출할 때는 `develop`에서 `main`으로 PR을 합친 뒤 `main` 링크를 강사님 대시보드에 붙이고, 링크가 열리는지 확인합니다.
