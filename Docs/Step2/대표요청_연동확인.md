# 대표 요청 연동 확인 — 문의 한 건

화면을 붙이기 전에, 문의 한 건이 학부모의 접수부터 학부모가 답을 받을 때까지 API로 끊기지 않고 이어지는지 확인한 표다. 단계마다 [T12](유치온_T12_화면지도.md)의 화면 경로와 그 단계에서 부르는 API, DB 모드 시험 결과, 지금 웹이 그 API를 부르는지를 나란히 적었다. 웹 쪽은 #318(`ju-web`, 커밋 `4ffd922`, develop `cbde076`에 머지)의 코드를 보고 채웠다. 시험은 팀 서버와 같은 조건에서 돌렸다. 그래서 요청 에이전트는 대역(`agent_stub`)을 쓰고, 답변 작성기는 기본값(stub) 그대로 두며, 감독 모델은 쓰지 않는다.

## 1. 대표 요청

시험할 문의로는 가상 원 시드에 있는 보호자 요청 22개 가운데 GR-16을 골랐다. 하람 보호자(`parent-c4-15`)가 보낸 "내일 준비물 있나요?"다. 이 질문은 [기획서](../Step1/기획서.md) 2.2 MVP의 '문의 답변(통신문 근거·출처)'에 들어맞고, 답도 원 자료인 통신문(NT-2026-30 '1쪽 준비물')에 있다. 덕분에 나중에 답변 작성기를 그래프로 바꾸더라도, 같은 요청으로 근거가 붙은 초안이 나오는지까지 확인할 수 있다. 하늘의 "기침해요"는 질문이 아니라 알림장에 반영해 달라는 요청이어서 고르지 않았다.

## 2. 단계별 연동

시험 결과 칸에는 `tests/integration/db/test_request_flow_inquiry.py`의 `test_inquiry_from_parent_to_teacher_approval_and_back_to_parent`로 확인한 값을 적었다. 웹 칸에 나오는 파일은 모두 `apps/web/src/` 아래에 있다.

## 3. 민원은 무엇이 다른가

민원도 접수, 분류·배정, 회신 카드, 담임 승인까지는 문의와 같다. 다른 점은 위험 낱말 기준, 원장 보고, 학부모 확인 세 가지다. 먼저 위험도다. #326부터 위험 등급은 문의·상담에도 붙어서, 긴급·판단 필요 문의도 민원과 같이 초안 없는 담임 카드와 원장 보고 카드로 넘어간다. 민원만 다른 점은 '안전'·'신고'·'개인정보' 같은 낱말 하나만 있어도 위험으로 본다는 것이다. 코드 규칙(`app/core/request_rules.py`의 `classify`)이 본문 낱말을 보고 `risk_level`을 정하는데, `urgent`나 `uncertain`이 나오면 담임 카드와 함께 원장 보고 카드(`director_report`)도 만들고 요청을 `escalated`로 올린다. `uncertain`인 동안에는 담임이 승인할 수 없고, 보류·원장 보고를 하거나 위험 등급을 다시 분류(API 3.14)하는 것만 할 수 있다. 원장 보고 단계가 따로 있다는 점도 다르다. 원장이 지시를 남기면 그 지시가 담임 카드에 붙고, 요청은 다시 `awaiting_review`로 돌아온다. 마지막으로, 민원은 학부모 확인을 거쳐야 끝난다. 회신한 뒤 학부모가 '확인했어요'(`POST /requests/{id}/confirm`, 웹 `RequestDetailPage.tsx` 24·102줄)를 누르고 담임이 '처리 완료'(`complete`)를 해야 `completed`가 된다. 학부모가 확인하지 않았다면 이유를 적어야 하고, 이유가 없으면 409 `REASON_REQUIRED`가 돌아온다. 이 차이는 모의 모드에서 `tests/integration/api/test_flows.py`의 시험 5개(`test_complaint_approval_confirmation_completion`, `test_unconfirmed_complete_needs_reason_and_overview_counts`, `test_reclassify_uncertain_and_escalate`, `test_explicit_escalation_and_edit_approval`, `test_director_report_permission_instructions_reassign`)로 확인한다. DB 제약은 [DB 스키마 설계서](DB_스키마_설계서.md) 8.3의 F2·F3 시험에서 확인한다.

## 4. 화면 연결 남음

- 담임 답이 학부모 글처럼 보이는 문제는 API 쪽은 해결됐다. 사람이 쓴 글은 학부모 글이든 담임 답이든 `sender_type: "user"`이지만, #324부터 `messages[].sender_role`(`parent`·`teacher`·`director`)이 같이 내려온다(API 설계 3.2). 웹 요청 상세(`RequestDetailPage.tsx` 52~56줄)가 `sender_type` 대신 `sender_role`로 말풍선을 나누는 일만 남았다.
- 문의는 DB 모드에서 `sent_or_booked`("답변 도착")에서 끝난다. 처리 완료(`complete`)는 민원에만 쓸 수 있어서, T04 5.1 그림에 있는 `sent_or_booked → completed`로 가는 길이 지금 코드에는 없다. MVP에서는 '답변 도착'을 문의의 끝으로 두고 완료로 바꾸는 시점은 후속으로 미루는 쪽으로 팀 의견을 모으는 중이다(11/24 지혜님 제안, 성주님 동의). 답변 도착 뒤 학부모가 이어서 질문하면 지금은 글만 저장되고 담임 카드·알림이 다시 생기지 않아서, 이 부분은 백엔드에서 고친다.
- 학부모 요청 경로 세 개(`/parent/requests`, `/new`, `/:requestId`)는 #318 머지(develop `cbde076`)로 실제 화면이 되어, 1·7·9번 단계를 화면에서 해 볼 수 있다.
