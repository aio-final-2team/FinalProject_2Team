## 1. 공통 규칙

### 1.1 정한 규칙 (태웅, 11/17)

백엔드 형식만 바뀌는 것은 태웅이 정했다. 괄호 안의 '쪽'은 강사님이 11/16에 올린 'API 설계 문서 작성법'의 쪽 번호다.

1. **기준 파일**: FastAPI Pydantic 모델이 기준이다. `/docs`에서 뽑은 `contracts/openapi.yaml`은 생성물로 커밋하고, 화면 타입과 모의 API는 그 yaml에서 만든다. md 문서(이 계약표, T13 API 설계 문서)는 사람이 읽는 설명이며 `/docs`와 대조해 판을 올린다(19·25쪽).
2. **경로**: 모든 경로 앞에 `/api/v1`을 붙인다. 자원은 복수 명사로 쓰고 실행은 하위 경로 POST로 둔다(예: `POST /api/v1/cards/{id}/decisions`, `POST /api/v1/requests/{id}/slot-choices`, `POST /api/v1/daily-notes/send`). 소문자와 하이픈만 쓴다. 개별 경로 이름은 T13에서 정한다(10·13쪽).
3. **목록**: `?page=1&size=20&sort=-created_at`로 받고 `{ "items": [...], "total": 37, "page": 1, "size": 20 }`로 돌려준다. `size`는 기본 20·최대 100, `sort` 기본은 `-created_at`이다(11쪽). 받은함만 기본 정렬이 다르다(규칙 11). 반 아이 목록(API 30)은 페이지 없이 이름순 `items[]`만 돌려준다.
4. **400과 422**: 입력 형식·검증 오류는 FastAPI 기본대로 422 `VALIDATION_FAILED`로 답한다. 필수 정보가 빠진 요청은 오류가 아니라 요청 상태 `needs_info`로 정상 응답에 담는다. 400은 쓰지 않는다(18쪽). [제안] T46 투약은 교직원이 확인하므로 `received`와 `missing_fields`로 표시해요(T13 3.27).
5. **성공 코드**: 아래 표를 따른다(8·23쪽).

   | 경우 | 코드 | 이 문서의 해당 동작 |
   | --- | --- | --- |
   | 조회 | 200 | 내 요청 목록·요청 상세·알림장 보기·받은함·카드 상세·원장 현황·알림 목록 |
   | AI 처리 접수 | 202 | 요청 만들기(응답에 요청 ID와 스트림 주소, 결과는 요청 상세·SSE로 봄. 같은 `client_request_id`로 다시 보내면 200 + 기존 요청) · 알림장 초안(`input_id`로 작업 상태 조회, 같은 반·날짜는 200 + 기존 작업) · 자료 올리기(적재·충돌 검사, `document.status`로 조회) |
   | 그 밖의 생성 | 201 | 대화 이어 쓰기 |
   | 결정·확정 같은 실행 | 200 | 로그인 · 카드 결정 · 위험 등급 다시 분류 · 상담 시간 체크·확정 · '확인했어요' · 규칙 제안 결정 · 원장 보고 지시 · 재배정 · 알림장 고치기·확인·보내기 · 알림 읽음 |
   | 삭제 | 204 | 내 기억 삭제(API 32), 본문 없음 |

6. **추적 ID**: 요청 헤더 `X-Request-ID`에 담고, 없으면 서버가 만든다. 오류 응답·도구 호출·이력에는 같은 값을 `trace_id`로 남긴다. `request_id`는 학부모 요청 ID 뜻으로만 쓴다(16·22쪽).
7. **예시 ID**: 시드 고정 UUID와 데모 이름의 짝을 부록 A에 두고, 문서 예시·팀 자체 30문항·시드가 같은 값을 쓴다(17·24쪽).
8. **상세 명세 범위**: T13 API 설계 문서에서 핵심 6개(요청 만들기, 요청 상세·스트림, 카드 결정, 상담 시간 체크·확정, 민원 '확인했어요', 알림장 보내기)는 태웅이 8칸을 빈칸 없이 쓴다. 나머지는 목록 표와 예시 JSON만 둔다(16·27쪽).
9. **오류 code와 화면 문구**: 오류 `code` 목록은 태웅이 정한다(1.3). 화면에 띄울 문구는 화면이 `code`별로 정한다.
10. **AI 진행 문구**: 서버는 SSE `stage` 값만 보낸다. 문구는 화면이 `stage` 값별로 정한다(3장).
11. **`urgency`와 위험 등급**: `urgency`(감독 AI가 붙이는 급한 정도, 4.1)와 `risk_level`(문의·상담·민원 위험 등급)은 필드가 달라 충돌하지 않는다. 받은함 맨 위 정렬은 `risk_level = urgent` 기준이다. 화면에서 '긴급'이라는 말은 위험 등급에만 쓴다.
12. **문서 충돌과 원에 남은 답**: 문서가 충돌 확인 대기(`conflict_pending`)가 되면 그 문서를 쓴 원에 남은 답도 무효가 된다(안전 쪽). 지금 DB 트리거가 이미 이렇게 동작한다(문서가 `active`에서 다른 상태로 바뀌면 답을 `invalidated`로 바꿈).

### 1.3 오류 응답 형식 (모든 API 공통)

```json
{
  "error": {
    "code": "CARD_VERSION_CONFLICT",
    "message": "다른 사람이 먼저 카드를 처리했어요. 새로고침해 주세요.",
    "trace_id": "8f2c…",
    "details": { "current_version": 3 }
  }
}
```

| HTTP | `code` 예 | 언제 |
| --- | --- | --- |
| 401 | `UNAUTHENTICATED` | 토큰 없음·만료·무효 |
| 403 | `FORBIDDEN_ROLE` | 역할상 못 하는 일(예: 학부모가 카드 결정) |
| 404 | `NOT_FOUND` | 없거나, 다른 기관·반 자료 |
| 409 | `CARD_VERSION_CONFLICT` · `SLOT_TAKEN` · `SLOT_PAST` · `SLOT_NOT_CHOSEN` · `ALREADY_DECIDED` · `INVALID_TRANSITION` · `NOTE_BATCH_BLOCKED` · `REASON_REQUIRED` | 동시 처리·예약/유효 체크 겹침·이미 시작한 후보 체크/확정·학부모가 체크하지 않은 시간 확정·이미 결정됨·T04 전이 규칙에 없는 상태 변경·반에 아직 확인 안 된 알림장이 있어 일괄 발송 잠김(`details.blocked[]`)·학부모 미확인 민원을 이유 없이 처리 완료(6장 ⑦) |
| 422 | `VALIDATION_FAILED` | 입력 형식·검증 규칙에 어긋남(FastAPI 기본과 같음). `details.fields`에 칸 이름 |
| 503 | `UPSTREAM_UNAVAILABLE` | 모델·외부 API 장애. 요청은 저장되고 나중에 다시 처리 |

400은 쓰지 않는다. 필수 정보가 빠진 요청은 오류가 아니라 요청 상태 `needs_info`로 돌려준다(규칙 4). `message`는 서버가 주는 기본 한국어 문장이고, 화면에 띄울 문구는 화면이 `code`별로 정한다(규칙 9). `trace_id`는 요청 헤더 `X-Request-ID`와 같은 값이며, 이력·LangSmith에서 같은 호출을 찾을 때 쓴다(규칙 6).

## 2. 화면 ↔ 백엔드

### 2.1 학부모

| 하는 일 | 보냄 | 받음 | 권한 |
| --- | --- | --- | --- |
| 로그인 | `login_id`, `password` | `access_token`, `user { id, role, display_name, org_id, classroom_ids[] }`(담임만 담당 반, 대체 담임은 기간 안), `children[] { id, display_name, classroom_id }`(학부모) | 전체 |
| 요청 만들기 | `client_request_id`, `type`, `body`, `child_id`, `previous_request_id?`(끝난 요청을 다시 열 때, T04 2.1) | `request { id, status, stream_url }`(202, 규칙 5). 빠진 정보는 분류가 끝난 뒤 요청 상세의 `request.missing_fields[]`로 받음(SSE `done.request_status = needs_info`). 권한 밖 문의는 보호 조건을 통과하면 고정 안내 후 `sent_or_booked`·카드 없음(API 5.7) | 학부모 |
| 내 요청 목록 | `status`(선택) | `items[] { id, type, title, status, status_label, updated_at, next_action, hold_until? }` — `status_label`은 서버가 상태·담당 유무로 계산한 학부모 표시 이름(T13 3.2) | 자기 요청만 |
| 요청 상세 | — | `request`, `messages[] { id, sender_type, sender_role, body, created_at }`, `timeline[] { label, at }`, `consultation?` — 권한 밖 고정 안내는 `sender_type=agent`·`sender_role=null`(API 5.7). `timeline`은 학부모용 요약(T04 7.1). 상태가 바뀐 단계만 학부모 표시 이름으로 주고, 위험 등급·보류 이유·도구 호출·처리한 교직원은 넣지 않음. 반려면 `rejection { reason_code, reason_text }`(T04 2장 '처리할 수 없는 요청이에요 (이유)'), 회신이 나갔으면 `sources[] { document_title, location, effective_from }`(학부모 공개 문서만) | 자기 요청만 |
| 대화 이어 쓰기 | `body` | `message { id, sender_type, sender_role, body, created_at }`. 이력은 `message_added`. AI 처리 중에는 알림 없음. 검토·보류·원장 보고·정보 보완 중에는 열린 카드 담당(없으면 원장)에게 `parent_message`(“학부모가 글을 더 남겼어요”). 상담 시간 선택 중·예약 확정 뒤에는 담임에게 알림만. 문의·민원 회신 뒤(권한 밖 고정 안내 뒤도 포함)에는 최신 회신 카드를 다시 열거나 담임 카드 생성 → `awaiting_review`·`new_card`. 다시 연 초안은 `text=""`·`check_result=null`, 이전 답은 `draft.previous_text`로 남겨 직접 쓴 `edit_approve`로만 보냄(API 3.10) | 자기 요청만 |
| AI 진행 보기(스트리밍) | — | SSE 이벤트(3장) 중 `stage`·`done`·`error`만. 답변 글자(`token`)는 보내지 않음 | 자기 요청만 |
| 상담 가능 시간 체크(`POST /api/v1/requests/{id}/slot-choices`) | `slot_ids[]`(1~3개) 또는 `none_fit: true`(다른 시간 필요) + `preferred_times` | `slots[] { id, status: "chosen_by_parent" }` → 요청은 `awaiting_review`. `none_fit`이면 희망 시간과 겹치는 후보 우선·없으면 가까운 순으로 재계산하고 담임(없으면 원장)에게 `parent_message`. 담임 없는 카드도 후보가 있으면 체크 가능 | 자기 요청만 (T04 합의 1) |
| 민원 회신 '확인했어요' | — | `request { status, parent_confirmed_at }`. 상태는 `sent_or_booked` 그대로, 목록·상세·타임라인은 "확인함 · 선생님이 마무리하고 있어요" | 자기 민원만 (T04 합의 2) |
| 알림장 보기(`GET /api/v1/daily-notes?date=`) | `date` | `items[] { id, input_id, child_id, note_date, content, sent_at }`(input_id는 담임 입력 묶음 UUID) — `content.items[] { key, label, value, source { type, document_id?, document_title?, request_id? } }`(줄마다 값과 출처, API 설계 문서 3.7) | 내 아이 것만, 보낸 것(`sent`)만 |
| 알림 목록·읽음 | `notification_id` | `items[] { id, kind, title, body, request_id, subject_type?, subject_id?, read_at }` — `kind`는 T04 9장 11가지 + `slot_hold_expired`·`hold_resumed`(6장 ⑥·⑨) + `parent_message`(추가 글, T13 3.10) + T48 `consultation_ending`·`consultation_delayed`(T13 6.6.2), 알림장 알림은 `subject_type = "daily_note"` | 자기 알림만 |

학부모 화면은 서버 `status_label`을 쓴다. `received`·`classified`는 "접수됨"(분류 직후엔 아직 담당을 고르기 전이라 따로 나누지 않는다), 담임 배정 뒤 `assigned`는 "선생님께 전달됨"이다. `assigned`·`awaiting_review`·`on_hold`도 요청 담당(`assignee_id`)이 없으면 "담당 선생님 배정 중"이고, 재배정 뒤에는 "선생님 확인 중"·"확인이 늦어지고 있어요"로 돌아간다. 투약·귀가·상담의 기존 유형별 문구는 T13 3.2를 따른다. 담당자 ID를 학부모 응답에 더하지 않는다.

민원 `sent_or_booked`에 `parent_confirmed_at`이 있으면 목록·상세·타임라인은 "확인함 · 선생님이 마무리하고 있어요", 처리 완료 뒤에는 "완료"로 표시한다. 상담 예약 확정 알림은 `consultation_booked`("상담 예약 확정", 한국 날짜·시간), 새 담당의 재배정 알림은 `reassigned`("요청이 배정됐어요")다. 반려 `rejected`의 본문은 6장 ①의 사유 표시 이름과 `reason_text`를 ` · `로 잇는다. 이유 글이 없으면 표시 이름만 쓴다.

상담 확정은 상담 후보 카드 담당 교사만 한다. 재배정은 살아 있는 후보의 시각·체크를 보존하고 교사를 새 담당으로 맞춘다. 확정 409 `SLOT_TAKEN`은 충돌 후보만 폐기하고 나머지는 보존한 채 후보 재계산·요청 `needs_info`·학부모 알림·`slot_conflict_reproposed`를 저장한다. 카드 판은 1 올라가므로 새로 읽고 다시 체크한다. 상담 반려(`dismiss`)는 `chosen_by_parent` 후보를 폐기해 임시 점유를 푼다.

긴급 재분류는 열린 회신 카드의 `draft.text=""`·`check_result=null`·판 +1이며, 원장 보고 카드를 대상으로 재분류해도 회신 카드에 적용한다. 완료·반려한 옛 회신은 보존한다. `escalated.detail.reason`은 `risk`(위험·장애 인계), `repeat`(반복 민원), `manual`(사람 올리기·긴급 재분류)이다. 재분류에 적은 사람 이유는 `risk_reclassified.detail.reason`으로 구분한다.

원장 확인 대기(`escalated`)의 담임 `reply_draft`는 `in_progress`, 표시 이름은 목록·상세 모두 "원장 확인 중"이다. 완료·보류·미배정 판정 뒤, `uncertain` 판정 전에 적용하며 원장 보고 카드의 필터는 기존 그대로다. 필터 값 6종은 바꾸지 않는다. 원장 지시 등으로 `awaiting_review`가 되면 기존 위험 등급의 필터로 돌아간다.

### 2.3 알림장 아이별 메모·줄·확인 항목 (T13 v0.4.1)

API 22의 입력과 알림장 조회·고치기의 JSON 모양을 맞춘다. 상세는 [API 설계 문서 3.7·3.19~3.21](API_설계_문서.md)을 따른다.

| 필드 | 모양·규칙 |
| --- | --- |
| `child_memos[]` | 초안 생성 본문의 선택 목록. 생략하면 `[]` |
| `child_memos[].child_id` | UUID, 항목마다 필수. 같은 아이를 두 번 보내면 422 `VALIDATION_FAILED`. 다른 반·다른 기관·없는 아이도 422이고 `details.child_id`에 해당 ID를 넣음 |
| `child_memos[].memo` | 문자열, 항목마다 필수, 1~500자. 빈 문자열은 422. 메모가 없거나 공백뿐이면 `child` 줄을 만들지 않음 |
| `content.items[]` | 줄마다 `key`, `label`, `value`, `source`를 가짐. `key`는 `day`·`meal`·`medication`·`pickup`·`supplies`·`child`·`inquiry` |

초안 입구 함수 입력은 `{ input_id, note_date, classroom, activities, supplies, children: [{ child_id, display_name, memo, requests: [{ request_id, type, text }] }], menu }`다. `menu`는 `{ document_id, title, text }` 또는 null이다. `requests`는 서버가 같은 기관·반·아이의 보호자 요청 중 `medication`·`pickup`·`inquiry`를 모은다. `created_at`의 한국 날짜가 `note_date`인 요청만 넣고, `text`는 원문, 없으면 빈 목록이다. 모의 초안은 노을의 고정 귀가 요청(…70a) 하나를 빼고 `request_missed`·`sentence = null`·해당 `request_id`를 남긴다. 투약·귀가 등록·확인·완료는 T13 3.27의 팀 확인 전 초안이에요. 읽기 응답의 content.items[].request_status는 연결 요청의 현재 상태이고 PATCH에서 저장하지 않아요.

아이별 메모 저장 열은 `daily_note_inputs.child_memos`다. 0002에서 더한 `jsonb NOT NULL DEFAULT '[]'::jsonb`이며 `jsonb_typeof(child_memos) = 'array'` CHECK가 있다(DDL·DB 설계서 v0.8). 아이 UUID·중복·소속·메모 길이는 API가 검사한다. 0001은 그대로 두고, 0002를 되돌리면 이 열의 메모가 사라진다.

### 2.4 알림장 원본·다시 만들기·내 기억 (v0.11)

- API 31 GET /memories는 담임 본인의 지우지 않은 기억을 kind(rejection_reason·preference·tone)로 거른다. 공통 page·size·sort와 items·total·page·size를 쓴다. 각 기억은 id(정수)·kind·reason_code(null 가능)·content·structured·created_at이다.
- API 32 DELETE /memories/{memory_id}는 본인 기억의 deleted_at을 표시하고 204(본문 없음)로 답한다. 남의 것·다른 기관·없는 것·이미 지운 것은 404, 학부모·원장은 403이다.
- API 33 POST /daily-notes/drafts/{input_id}/regenerate는 본문 없이 저장 입력으로 다시 만든다. 202 RegenerateResponse(input_id·draft_status·error·kept_edited)이며 상태·결과 조회는 기존 API 23·24의 DraftResponse 그대로다. kept_edited는 접수 시 교사 수정으로 보존한 미확인 알림장 수(0 이상 정수)다. sent가 하나라도 있으면 409 INVALID_TRANSITION이다. ready와 교사 수정본(content ≠ ai_original 또는 daily_note_edited 이력)은 보존하고 나머지 draft·needs_check만 갱신한다. failed와 시간 제한을 넘은 queued·running은 재접수하며, 제한 안의 실행은 현재 상태만 돌려주고 다시 실행하지 않는다.
- 0003의 daily_notes.ai_original은 선생님이 받은 마지막 AI 초안이다. 교사 수정·확인·발송 때 유지하고 수정하지 않은 미확인 알림장을 재생성할 때 새 초안으로 바꾼다. 기존 행은 적용 시점 content로 채운다. NoteView의 공개 응답 칸은 그대로다.
- events.daily_note_id(기관 복합 FK)에 daily_note_drafted·daily_note_edited·daily_note_confirmed·daily_note_sent를 남긴다. daily_note_edited는 내용이 실제로 바뀔 때만 남기고, 확인 취소는 returned로 ready→draft, 검사 해소는 checked로 needs_check→draft를 남긴다. 재생성 요청자는 반 묶음 카드 draft.regenerated_by와 새 drafted의 detail.regenerated_by에 저장한다. 기억 추출·학습·새 규칙 제안은 기억 AI 몫이며 이번 백엔드는 저장·조회·삭제·이력만 한다.

## 4. 백엔드 ↔ 에이전트 (Function Calling 도구)

에이전트는 기관이 고정된 서비스 권한으로 도구를 부른다. 도구는 DB를 직접 열지 않고 백엔드 함수를 거친다. 모든 도구 호출은 `events`에 `tool_called` 또는 `tool_failed`로 남는다.

'받는 값'은 두 가지로 나눈다. **모델이 채우는 값**은 모델에게 보이는 함수 인자이고, 팀 자체 30문항 v0.5의 도구 정의와 같다(4.2). **(백엔드)** 표시가 붙은 값은 모델에게 보이지 않고 백엔드가 지금 요청·로그인 정보로 채운다. 그래서 모델이 다른 기관·다른 학부모의 ID를 넣어도 범위를 넘지 못한다.

'실패 코드'는 T13(태웅), '실패 시 행동'은 T14(영민)가 채운다(6장 ④). 아직 비어 있는 칸에는 채울 작업 번호를 적었다. T13 칸은 [API 설계 문서](API_설계_문서.md) 5.4에 코드·`retryable`·기본 행동까지 채웠다(11/18). ### 4.1 에이전트가 내는 결과 형식

| 결과 | 필드 |
| --- | --- |
| 분류(감독 AI) | `type`, `urgency`(`low`·`normal`·`high`·`urgent`), `topic_key`, `assignee_role`, `missing_fields[]`, `handoff_reason?`(모호·긴급·고위험이면 사람에게 바로). 문의·상담·민원이면 `risk_level`(`normal`·`urgent`·`uncertain`), `risk_category?`(긴급 4가지), `risk_confidence`(0~1), `repeat_count`(같은 반·30일·같은 주제), `out_of_scope_kind?`(`payment`·`others_privacy`·`other_family`·`other_teacher`, 그 외 null) |
| 답변 초안(자료 AI) | `text`, `evidence[] { chunk_id, quote }`, `no_evidence`(근거 없음이면 참), `conflict`(문서 충돌이면 참) |
| 검사(검사 AI) | `passed`, `issues[] { field, problem }`(출처·날짜·대상·누락·민감정보), `attempt` |

권한 밖 고정 안내는 긴급·판단 필요가 아니고 주제가 `peer_conflict`·`safety`·`health_hygiene`이 아니며 본문에 “우리 아이”·“우리 애”·“저희 아이”가 없을 때만 쓴다. 문의는 API 5.7의 네 고정 문구 중 하나를 agent 메시지로 남기고 `sent_or_booked`·학부모 알림·`out_of_scope_answered(detail.kind)` 이력으로 끝낸다. 담임 승인 카드·승인 기록은 만들지 않는다. 상담 `other_teacher`는 같은 조건에서 안내만 더하고 담임 시간 선택 흐름을 유지한다. 다른 상담·민원은 평소 흐름이다.

AI 실패(`ai_failed`)·3분 초과(`ai_timeout`)·카드 누락(`card_missing`) 인계 때는 모델을 다시 부르지 않고 코드 규칙으로 `topic_key`·`urgency`·`risk_level`·`risk_category`를 다시 저장한다. 정상 경로와 같은 유효한 담임에게 초안 없는 회신 카드(`pending`)를 배정한다. 일반은 요청 `awaiting_review`·담임 `new_card` 알림, 긴급·판단 필요는 요청 `escalated`·원장 보고 카드·담임과 원장 위험 알림이다. 유효한 담임이 없을 때만 회신 카드가 `unassigned`이고 일반 알림은 원장에게 간다. 인계 이유는 `events.detail.handoff_reason`에 남긴다(API 6.1·6.3).

### 4.2 팀 자체 30문항 도구(T06)와의 짝

강사님 11/17 피드백(FB-001-1)에 따라 이름과 인자를 맞췄다. 기준 파일은 팀 자체 30문항 v0.5(`Docs/Step2/2팀_유치온_자체평가_30문항.json`, 11/17 강사님 제출본, PR #235로 11/18 develop 머지)이다. v0.5는 도구 이름을 이미 계약 쪽으로 바꿨으므로, 계약은 모델이 채우는 값을 v0.5에 맞추고 백엔드가 채우는 값만 따로 적었다. 30문항 쪽은 인혜가 11/18 `create_card`의 `category` 칸 이름을 `topic_key`로 바꿨다(PR #235). 그 밖의 문항·정답은 바꾸지 않는다(NFR-09).

| 30문항 v0.5 도구 | 계약 4장 | 맞춘 내용 |
| --- | --- | --- |
| `search_documents` | 같은 이름 | 모델 값 = `kindergarten_id`·`doc_type`·`query`. 계약의 `doc_types[]?`(여러 개·선택)를 `doc_type`(하나·필수)으로 바꿈. `classroom_id`·`top_k`는 백엔드 |
| `find_consult_slots` | 같은 이름 | 모델 값 = `teacher_id`·`date`. 계약의 기간(`from`·`to`)을 날짜 하루로 바꿈. `request_id`·`rules[]`는 백엔드 |
| `request_consultation` | 새로 넣음 | 학부모가 고른 시간으로 상담 요청. 확정은 담임의 `book_slot` |
| `get_my_requests` | 새로 넣음 | 본인 요청 상태 조회. 화면 2.1 '내 요청 목록'과 같은 값 |
| `create_card` | 같은 이름 | 모델 값 = `request_type`·`topic_key`·`summary`·`urgency`·`escalate_to_director`. 계약의 `kind`·`assignee_id`·`request_id`는 백엔드가 이 값으로 정함 |

값 이름도 맞췄다.

- `topic_key`는 요청의 `topic_key`에 그대로 저장한다(6장 ②). 계약 값은 주제 10개 + `other`이고, 30문항 v0.5 도구 정의에는 그중 6개(`safety`·`meal`·`teacher`·`belongings`·`fee`·`other`)만 있다. 30문항은 평가 중이라 값 목록과 정답을 그대로 두고(인혜, PR #252 메모), 새 5개는 영민이 T14 평가 문항으로 확인한다. 문의(`inquiry`) 카드의 `topic_key`는 30문항 채점에서 뺀다.
- `create_card`의 `urgency`는 `normal`·`urgent` 2개이고, 요청의 `urgency`(4.1 분류의 `low`·`normal`·`high`·`urgent` 중)에 같은 값으로 들어간다. 위험 등급(`risk_level`·`risk_category`)은 분류 단계(`route_request`)가 정한다. DB가 `risk_level = urgent`면 `risk_category`(긴급 4가지)를 꼭 요구하는데 `create_card`에는 그 값이 없어서다(DB 설계서 2.2).
- `escalate_to_director = true`면 카드 종류는 `director_report`, 담당은 원장이다.

돌려주는 값과 오류는 30문항의 가짜 응답(`mock_responses`)이 채점용으로 줄인 모양이다. 실제 도구는 아래처럼 돌려준다.

| 30문항 가짜 응답 | 실제 도구 응답 |
| --- | --- |
| `{"error": "timeout"}` (F01) | 1.3 오류 형식, `code = UPSTREAM_UNAVAILABLE`, `retryable = true` |
| `{"error": "save_failed"}` (F04) | 1.3 오류 형식, `code = SAVE_FAILED`(API 설계 문서 5.2), `retryable = true` |
| `{"slots": []}` (F02) | 같은 모양. `slots[]`가 빈 목록이면 에이전트는 다른 날을 묻거나 담임 카드로 넘김(T14) |
| `search_documents`의 `{"conflict": true, "results": [{ title, effective_date, … }]}` (F03) | `chunks[]`만 돌려준다. 30문항의 `title`·`effective_date`는 계약의 `document_title`·`effective_from`이다. 문서끼리 다르다는 판단(`conflict`)은 자료 AI가 답변 초안(4.1)에 표시한다 |

30문항에 없는 계약 도구(`route_request`·`notify_staff`·`get_memory`·`propose_rule`·`check_draft`·`return_to_step`·`book_slot`·`get_law_article`·`get_daily_note`·`find_saved_answer`)는 에이전트 안쪽 단계나 교직원 쪽 도구라 학부모 질문 채점 대상이 아니다. v0.2의 옛 이름(`lookup_notice`·`get_consultation_slots`·`prepare_*` 등)은 v0.5에서 없어졌다.

## T46 투약·귀가 계약 추가 — [제안] 팀 확인 전 초안(v0.17)

FR-16·AC-09의 미등록 인계자·필수값 누락을 표시해요. 아래 선택은 팀 확인 전 [제안]이에요.
POST /requests는 medication·pickup을 받아요. 등록 인계자는 pickup_guardian_id, 미등록이면 pickup_name·pickup_relation을 보내요.
이름·관계만 있어도 접수해요. 둘 다 없는 기존 귀가 시드도 unregistered_pickup=true로 표시하고 교직원이 확인해요.
투약 medication_name·medication_dose·medication_time은 각 100자 이하 선택 칸이에요. 없거나 공백이면 missing_fields에 넣어요.
누락 자체는 오류가 아니고 received예요. AI가 본문에서 채우지 않아요. 교직원이 대화와 누락을 확인한 뒤 결정해요.
API 34는 GET /children/{child_id}/pickup-guardians, API 35는 교직원 GET /care-requests예요.
목록에는 child_id(UUID)·child_name(string, children.display_name의 현재 이름)·version·unregistered_pickup·missing_fields를 더해요. sort는 -created_at(기본)·created_at·-updated_at·updated_at이에요.
API 36 POST /requests/{request_id}/care-decisions는 decision=confirm·complete·reject와 본 version(양의 정수 필수)을 받아요.
등록 인계자의 confirm·complete에는 같은 UUID를 다시 보내고 미등록·reject이면 생략해요. 잘못된 명시 UUID는 422지만 미등록 자체는 막지 않아요.
received→assigned→completed예요. 확인 전 완료는 409예요. 미등록 confirm은 '미등록 인계자 확인' 이력과 원장 알림 1건을 남겨요.
확인 당시 인계자 기록을 보존해요. 그 뒤 계정 비활성·연결 해제는 실제 complete를 막지 않아요.
care.version은 최초 1·보호자 추가 글이나 구조화 입력 수정마다 +1인 입력 판이에요. 확인·완료 자체는 올리지 않아요.
추가 글은 확인을 지우고 received로 돌려 담당자 알림 1건을 남겨요. 교직원은 대화를 읽고 다시 확인해요.
옛 판의 confirm·complete·reject·입력 수정은 409 CARD_VERSION_CONFLICT예요. 요청 행 잠금 안에서 판을 확인해요.
추가 글은 본문·구조화 입력을 바꾸지 않고 AI도 실행하지 않아요. 글만으로 자동 취소하지 않아요. 완료·반려·취소 뒤 글은 409예요.
reject는 received·assigned에서만 가능하고 reason_text(1~1000자, 공백 불가)가 필수예요. rejected와 dismissed(care_decision=reject·reason_text·version)를 남겨요. 상세 rejection은 {reason_code:"other",reason_text}이고 알림 본문에도 사유를 넣어요.
API 50 POST /requests/{request_id}/cancel은 자기 투약·귀가 요청만, completed·rejected 전까지 본문 없이 불러요. rejected + cancelled(detail.cancelled_by_parent=true)이고 표시는 "취소함"이에요. 원문·대화·기존 확인·입력 판을 보존해요.
API 51 PATCH /requests/{request_id}/care는 자기 요청의 received·assigned에서 version과 고칠 칸 하나 이상을 받아요. 생략은 유지, null은 비움, 다른 유형 칸·알 수 없는 칸은 422예요. 원문·대화는 보존해요.
care_detail·missing_fields를 다시 저장하고 입력 판 +1·confirmed_at 비움·received·care_updated(fields·version)·담당자 care_requested 알림이에요. 등록 인계자 유효성을 다시 검사하고 snapshot을 갱신해요. UUID 변경·해제 때 이전 이름·관계를 지우며 미등록 인계자로 바뀌면 원장 경고를 다시 남겨요. 이름·관계가 같은 경고는 confirm과 중복 제거해요.
취소·수정·반려도 확인·완료와 같은 요청 행 잠금 안에서 상태·이력·알림을 함께 저장해요. GET /care-requests의 status 필터에는 rejected도 포함해요.
상세 care는 version·인계자 UUID/이름/관계·unregistered_pickup·투약 세 칸·missing_fields·확인/완료 시각이에요.
교직원 신원은 넣지 않아요. 부모는 자기 요청, 담임은 현재 반, 원장은 기관만 봐요.
접수·정정·미등록 원장 경고는 care_requested, 학부모 확인은 care_confirmed, 완료는 completed, 교직원 반려는 학부모에게 care_rejected, 학부모 취소는 담당자(없으면 원장)에게 cancelled예요.
귀가는 근무 밖·주말과 실패 재시도도 즉시, 투약 교직원 알림은 근무 시간을 따라요. 지시·대화 원문은 알림에 싣지 않아요.
알림장 request_status는 현재 상태를 읽고 content·AI 원본은 보존해요. 목록은 한 연결·한 요청 상태 조회예요.
구조화 입력은 requests.care_detail에 저장해요. 접수 events.detail에는 값 없이 fields(칸 이름 목록)·trace_id만 남겨요. 상세 care·누락 목록은 care_detail에서, 확인 당시 인계자와 추가 글의 판은 기존 이력에서 읽어요. 0012가 care_detail을 추가하고 옛 접수 입력을 이관해요. 알림장 투약·귀가 줄은 계속 보호자 요청 본문을 그대로 옮겨요.
