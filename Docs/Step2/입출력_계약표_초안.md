T13(11/19~20)에서 이 표를 Pydantic 모델로 옮기고, `/docs`에서 뽑은 `contracts/openapi.yaml`로 모의 API와 화면 타입(`openapi-typescript`)을 만든다(1.1 규칙 1).

## 1. 공통 규칙

### 1.1 정한 규칙 (태웅, 11/17)

백엔드 형식만 바뀌는 것은 태웅이 정했다. 괄호 안의 '쪽'은 강사님이 11/16에 올린 'API 설계 문서 작성법'의 쪽 번호다.

1. **기준 파일**: FastAPI Pydantic 모델이 기준이다. `/docs`에서 뽑은 `contracts/openapi.yaml`은 생성물로 커밋하고, 화면 타입과 모의 API는 그 yaml에서 만든다. md 문서(이 계약표, T13 API 설계 문서)는 사람이 읽는 설명이며 `/docs`와 대조해 판을 올린다(19·25쪽).
2. **경로**: 모든 경로 앞에 `/api/v1`을 붙인다. 자원은 복수 명사로 쓰고 실행은 하위 경로 POST로 둔다(예: `POST /api/v1/cards/{id}/decisions`, `POST /api/v1/requests/{id}/slot-choices`, `POST /api/v1/daily-notes/send`). 소문자와 하이픈만 쓴다. 개별 경로 이름은 T13에서 정한다(10·13쪽).
3. **목록**: `?page=1&size=20&sort=-created_at`로 받고 `{ "items": [...], "total": 37, "page": 1, "size": 20 }`로 돌려준다. `size`는 기본 20·최대 100, `sort` 기본은 `-created_at`이다(11쪽). 받은함만 기본 정렬이 다르다(규칙 11).
4. **400과 422**: 입력 형식·검증 오류는 FastAPI 기본대로 422 `VALIDATION_FAILED`로 답한다. 필수 정보가 빠진 요청은 오류가 아니라 요청 상태 `needs_info`로 정상 응답에 담는다. 400은 쓰지 않는다(18쪽).
5. **성공 코드**: 아래 표를 따른다(8·23쪽).

   | 경우 | 코드 | 이 문서의 해당 동작 |
   | --- | --- | --- |
   | 조회 | 200 | 내 요청 목록·요청 상세·알림장 보기·받은함·카드 상세·원장 현황·알림 목록 |
   | AI 처리 접수 | 202 | 요청 만들기(응답에 요청 ID와 스트림 주소, 결과는 요청 상세·SSE로 봄. 같은 `client_request_id`로 다시 보내면 200 + 기존 요청) · 알림장 초안(AI 생성, 끝나면 SSE·알림) · 자료 올리기(적재·충돌 검사, `document.status`로 조회) |
   | 그 밖의 생성 | 201 | 대화 이어 쓰기 |
   | 결정·확정 같은 실행 | 200 | 로그인 · 카드 결정 · 위험 등급 다시 분류 · 상담 시간 체크·확정 · '확인했어요' · 규칙 제안 결정 · 원장 보고 지시 · 재배정 · 알림장 고치기·확인·보내기 · 알림 읽음 |
   | 삭제 | 204 | MVP 계약에는 아직 없음 |

6. **추적 ID**: 요청 헤더 `X-Request-ID`에 담고, 없으면 서버가 만든다. 오류 응답·도구 호출·이력에는 같은 값을 `trace_id`로 남긴다. `request_id`는 학부모 요청 ID 뜻으로만 쓴다(16·22쪽).
7. **예시 ID**: 시드 고정 UUID와 데모 이름의 짝을 부록 A에 두고, 문서 예시·팀 자체 30문항·시드가 같은 값을 쓴다(17·24쪽).
8. **상세 명세 범위**: T13 API 설계 문서에서 핵심 6개(요청 만들기, 요청 상세·스트림, 카드 결정, 상담 시간 체크·확정, 민원 '확인했어요', 알림장 보내기)는 태웅이 8칸을 빈칸 없이 쓴다. 나머지는 목록 표와 예시 JSON만 둔다(16·27쪽).
9. **오류 code와 화면 문구**: 오류 `code` 목록은 태웅이 정한다(1.3). 화면에 띄울 문구는 화면이 `code`별로 정한다.
10. **AI 진행 문구**: 서버는 SSE `stage` 값만 보낸다. 문구는 화면이 `stage` 값별로 정한다(3장).
11. **`urgency`와 위험 등급**: `urgency`(감독 AI가 붙이는 급한 정도, 4.1)와 `risk_level`(민원 위험 등급)은 필드가 달라 충돌하지 않는다. 받은함 맨 위 정렬은 `risk_level = urgent` 기준이다. 화면에서 '긴급'이라는 말은 위험 등급에만 쓴다.
12. **문서 충돌과 원에 남은 답**: 문서가 충돌 확인 대기(`conflict_pending`)가 되면 그 문서를 쓴 원에 남은 답도 무효가 된다(안전 쪽). 지금 DB 트리거가 이미 이렇게 동작한다(문서가 `active`에서 다른 상태로 바뀌면 답을 `invalidated`로 바꿈).

| --- | --- |

| ID | UUID 문자열: 기관·반·계정·아이·요청·카드·문서·상담실·상담 예약·자동 규칙·원에 남은 답·알림장(교사 입력·아이별 알림장). 정수(JSON 숫자): 대화 메시지·문서 조각·결정 기록·이력·교사 일정·상담 후보(`slot_id`)·기억·알림·평가 실행. 복합 PK 표 4개(`classroom_staff`·`child_guardians`·`card_evidence`·`saved_answer_sources`)는 두 ID 짝. DB 설계서 2.0 ID 형식 표(uuid 13 · bigint 9 · 복합 PK 4)와 같음 |
| 시각 | ISO 8601, 한국 시간 오프셋 포함(예: `2026-12-01T15:00:00+09:00`) |
| 목록 | 규칙 3: `page`·`size`·`sort` → `items`·`total`·`page`·`size` |
| 추적 ID | 규칙 6: 요청 헤더 `X-Request-ID` = 응답·도구·이력의 `trace_id` |
| 같은 제출 두 번 | 요청 만들기는 화면이 만든 `client_request_id`를 꼭 보냄. 같은 값이면 200으로 처음 만든 요청을 그대로 돌려줌 |
| 카드 결정 | 화면이 본 카드 `version`을 같이 보냄. 그사이 카드가 바뀌었으면 409 |
| 다른 기관·다른 반 자료 | 있는지 없는지도 알리지 않도록 404로 답함(권한 거부는 이력에 남김. DB 설계서 4.4 차단 시험과 같음) |

### 1.3 오류 응답 형식 (모든 API 공통)

```json
{
  "error": {
    "code": "CARD_VERSION_CONFLICT",
    "message": "다른 사람이 먼저 카드를 처리했어요. 새로고침해 주세요.",
    "trace_id": "8f2c…",
    "details": { "current_version": 3 }
  }
}
```

| HTTP | `code` 예 | 언제 |
| --- | --- | --- |
| 401 | `UNAUTHENTICATED` | 토큰 없음·만료·무효 |
| 403 | `FORBIDDEN_ROLE` | 역할상 못 하는 일(예: 학부모가 카드 결정) |
| 404 | `NOT_FOUND` | 없거나, 다른 기관·반 자료 |
| 409 | `CARD_VERSION_CONFLICT` · `SLOT_TAKEN` · `SLOT_NOT_CHOSEN` · `ALREADY_DECIDED` · `INVALID_TRANSITION` · `NOTE_BATCH_BLOCKED` · `REASON_REQUIRED` | 동시 처리·예약 겹침·학부모가 체크하지 않은 시간 확정·이미 결정됨·T04 전이 규칙에 없는 상태 변경·반에 아직 확인 안 된 알림장이 있어 일괄 발송 잠김(`details.blocked[]`)·학부모 미확인 민원을 이유 없이 처리 완료(6장 ⑦) |
| 422 | `VALIDATION_FAILED` | 입력 형식·검증 규칙에 어긋남(FastAPI 기본과 같음). `details.fields`에 칸 이름 |
| 503 | `UPSTREAM_UNAVAILABLE` | 모델·외부 API 장애. 요청은 저장되고 나중에 다시 처리 |

400은 쓰지 않는다. 필수 정보가 빠진 요청은 오류가 아니라 요청 상태 `needs_info`로 돌려준다(규칙 4). `message`는 서버가 주는 기본 한국어 문장이고, 화면에 띄울 문구는 화면이 `code`별로 정한다(규칙 9). `trace_id`는 요청 헤더 `X-Request-ID`와 같은 값이며, 이력·LangSmith에서 같은 호출을 찾을 때 쓴다(규칙 6).

## 2. 화면 ↔ 백엔드

### 2.1 학부모

| 하는 일 | 보냄 | 받음 | 권한 |
| --- | --- | --- | --- |
| 로그인 | `login_id`, `password` | `access_token`, `user { id, role, display_name, org_id }`, `children[]` | 전체 |
| 요청 만들기 | `client_request_id`, `type`, `body`, `child_id`, `previous_request_id?`(끝난 요청을 다시 열 때, T04 2.1) | `request { id, status, stream_url }`(202, 규칙 5). 빠진 정보는 분류가 끝난 뒤 요청 상세의 `request.missing_fields[]`로 받음(SSE `done.request_status = needs_info`) | 학부모 |
| 내 요청 목록 | `status`(선택) | `items[] { id, type, title, status, status_label, updated_at, next_action, hold_until? }` — `status_label`은 T04 2장 학부모 표시 이름 | 자기 요청만 |
| 요청 상세 | — | `request`, `messages[]`, `timeline[] { label, at }`, `consultation?` — `timeline`은 학부모용 요약(T04 7.1). 상태가 바뀐 단계만 학부모 표시 이름으로 주고, 위험 등급·보류 이유·도구 호출·처리한 교직원은 넣지 않음 | 자기 요청만 |
| 대화 이어 쓰기 | `body` | `message { id, sender_type, body, created_at }` | 자기 요청만 |
| AI 진행 보기(스트리밍) | — | SSE 이벤트(3장) 중 `stage`·`done`·`error`만. 답변 글자(`token`)는 보내지 않음 | 자기 요청만 |
| 상담 가능 시간 체크(`POST /api/v1/requests/{id}/slot-choices`) | `slot_ids[]`(1~3개) 또는 `none_fit: true`(다른 시간 필요) + `preferred_times` | `slots[] { id, status: "chosen_by_parent" }` → 요청은 `awaiting_review`. `none_fit`이면 후보를 다시 계산 | 자기 요청만 (T04 합의 1) |
| 민원 회신 '확인했어요' | — | `request { status, parent_confirmed_at }` | 자기 민원만 (T04 합의 2) |
| 알림장 보기(`GET /api/v1/daily-notes?date=`) | `date` | `items[] { id, child_id, note_date, content, sent_at }` | 내 아이 것만, 보낸 것(`sent`)만 |
| 알림 목록·읽음 | `notification_id` | `items[] { id, kind, title, body, request_id, subject_type?, subject_id?, read_at }` — `kind`는 T04 9장 11가지 + `slot_hold_expired`·`hold_resumed`(6장 ⑥·⑨), 알림장 알림은 `subject_type = "daily_note"` | 자기 알림만 |

### 2.2 교사·원장

| 하는 일 | 보냄 | 받음 | 권한 |

| 규칙 제안 결정 | `rule_id`, `decision`(`activate`·`decline`) | `rule { id, status }` | 규칙 주인 |
| 원장 보고 지시 | `card_id`(원장 보고 카드), `version`, `instruction`(필수) | `card { status: "done", version }`, `request { status: "awaiting_review" }` — 지시는 `approvals`에 `decision = instruct`, 내용은 `reason_text`로 남고 담임 카드에 붙음 | 원장·원감 |

## 3. AI 진행 스트리밍 (SSE)

| 항목 | 안 |
| --- | --- |
| 경로 예 | 학부모 `GET /api/v1/requests/{id}/stream` · 교직원 카드 화면 `GET /api/v1/cards/{id}/stream` |
| 읽는 법 | 토큰을 헤더로 보내야 하므로 브라우저 `EventSource` 대신 `fetch` 스트림으로 읽음 |
| 이벤트 | `stage`(단계 바뀜) · `token`(답변 글자) · `card`(카드가 생김) · `done`(끝) · `error`(오류, 1.3과 같은 형식) |
| 누가 무엇을 받나 | 학부모 스트림은 `stage`·`done`·`error`만. `token`·`card`는 교직원 카드 화면 스트림에서만 보낸다. 담임 승인 전 초안이 학부모에게 나가지 않게 하기 위해서다(T04 3.2 자동 회신 금지, 5.2 첫 답은 담임 승인) |

```text
event: stage
data: {"stage": "searching", "at": "2026-12-01T10:00:02+09:00"}

event: token                       ← 교직원 카드 화면 스트림만
data: {"text": "12월 체험학습은 "}

event: done
data: {"request_status": "awaiting_review"}
```

`stage` 값은 요청 상태가 아니라 AI 처리 단계다. `classifying`(분류) · `searching`(근거 검색) · `drafting`(초안) · `checking`(검사)을 쓰고, 끝나면 바뀐 요청 상태를 `done.request_status`로 보낸다(T04 1장 "상태가 아니라 진행 표시", NFR-10). 서버는 문구를 보내지 않고, 화면이 `stage` 값별 문구를 정한다(1.1 규칙 10).

## 4. 백엔드 ↔ 에이전트 (Function Calling 도구)

에이전트는 기관이 고정된 서비스 권한으로 도구를 부른다. 도구는 DB를 직접 열지 않고 백엔드 함수를 거친다. 모든 도구 호출은 `events`에 `tool_called` 또는 `tool_failed`로 남는다.

'받는 값'은 두 가지로 나눈다. **모델이 채우는 값**은 모델에게 보이는 함수 인자이고, 팀 자체 30문항 v0.5의 도구 정의와 같다(4.2). **(백엔드)** 표시가 붙은 값은 모델에게 보이지 않고 백엔드가 지금 요청·로그인 정보로 채운다. 그래서 모델이 다른 기관·다른 학부모의 ID를 넣어도 범위를 넘지 못한다.

'실패 코드'는 T13(태웅), '실패 시 행동'은 T14(영민)가 채운다(6장 ④). 아직 비어 있는 칸에는 채울 작업 번호를 적었다. T13은 실패 코드마다 '다시 해볼 실패'인지 '다시 해도 안 되는 실패'인지 나눠 적고, 도구 실패 응답에 `retryable`(참·거짓)로 담는다. 행동 칸의 기본값은 다시 해볼 실패면 1번 다시 부르고, 그래도 실패하거나 다시 해도 안 되는 실패면 사람 카드로 넘기는 것이다.

### 4.2 팀 자체 30문항 도구(T06)와의 짝

강사님 11/17 피드백(FB-001-1)에 따라 이름과 인자를 맞췄다. 기준 파일은 팀 자체 30문항 v0.5(`Docs/Step2/2팀_유치온_자체평가_30문항.json`, 11/17 강사님 제출본, PR #235로 11/18 develop 머지)이다. v0.5는 도구 이름을 이미 계약 쪽으로 바꿨으므로, 계약은 모델이 채우는 값을 v0.5에 맞추고 백엔드가 채우는 값만 따로 적었다. 30문항 쪽은 인혜가 11/18 `create_card`의 `category` 칸 이름을 `topic_key`로 바꿨다(PR #235). 그 밖의 문항·정답은 바꾸지 않는다(NFR-09).

| 30문항 v0.5 도구 | 계약 4장 | 맞춘 내용 |
| --- | --- | --- |
| `search_documents` | 같은 이름 | 모델 값 = `kindergarten_id`·`doc_type`·`query`. 계약의 `doc_types[]?`(여러 개·선택)를 `doc_type`(하나·필수)으로 바꿈. `classroom_id`·`top_k`는 백엔드 |
| `find_consult_slots` | 같은 이름 | 모델 값 = `teacher_id`·`date`. 계약의 기간(`from`·`to`)을 날짜 하루로 바꿈. `request_id`·`rules[]`는 백엔드 |
| `request_consultation` | 새로 넣음 | 학부모가 고른 시간으로 상담 요청. 확정은 담임의 `book_slot` |
| `get_my_requests` | 새로 넣음 | 본인 요청 상태 조회. 화면 2.1 '내 요청 목록'과 같은 값 |
| `create_card` | 같은 이름 | 모델 값 = `request_type`·`topic_key`·`summary`·`urgency`·`escalate_to_director`. 계약의 `kind`·`assignee_id`·`request_id`는 백엔드가 이 값으로 정함 |

값 이름도 맞췄다.

- `topic_key`는 요청의 `topic_key`에 그대로 저장한다(6장 ②). 계약 값은 주제 10개 + `other`이고, 30문항 v0.5 도구 정의에는 그중 6개(`safety`·`meal`·`teacher`·`belongings`·`fee`·`other`)만 있다. 30문항은 평가 중이라 값 목록과 정답을 그대로 두고(인혜, PR #252 메모), 새 5개는 영민이 T14 평가 문항으로 확인한다. 문의(`inquiry`) 카드의 `topic_key`는 30문항 채점에서 뺀다.
- `create_card`의 `urgency`는 `normal`·`urgent` 2개이고, 요청의 `urgency`(4.1 분류의 `low`·`normal`·`high`·`urgent` 중)에 같은 값으로 들어간다. 민원 위험 등급(`risk_level`·`risk_category`)은 분류 단계(`route_request`)가 정한다. DB가 `risk_level = urgent`면 `risk_category`(긴급 4가지)를 꼭 요구하는데 `create_card`에는 그 값이 없어서다(DB 설계서 2.2).
- `escalate_to_director = true`면 카드 종류는 `director_report`, 담당은 원장이다.

돌려주는 값과 오류는 30문항의 가짜 응답(`mock_responses`)이 채점용으로 줄인 모양이다. 실제 도구는 아래처럼 돌려준다.

| 30문항 가짜 응답 | 실제 도구 응답 |
| --- | --- |
| `{"error": "timeout"}` (F01) | 1.3 오류 형식, `code = UPSTREAM_UNAVAILABLE`, `retryable = true` |
| `{"error": "save_failed"}` (F04) | 1.3 오류 형식, 저장 실패 코드(이름은 T13에서 확정), `retryable = true` |
| `{"slots": []}` (F02) | 같은 모양. `slots[]`가 빈 목록이면 에이전트는 다른 날을 묻거나 담임 카드로 넘김(T14) |
| `search_documents`의 `{"conflict": true, "results": [{ title, effective_date, … }]}` (F03) | `chunks[]`만 돌려준다. 30문항의 `title`·`effective_date`는 계약의 `document_title`·`effective_from`이다. 문서끼리 다르다는 판단(`conflict`)은 자료 AI가 답변 초안(4.1)에 표시한다 |

30문항에 없는 계약 도구(`route_request`·`notify_staff`·`get_memory`·`propose_rule`·`check_draft`·`return_to_step`·`book_slot`·`get_law_article`·`get_daily_note`·`find_saved_answer`)는 에이전트 안쪽 단계나 교직원 쪽 도구라 학부모 질문 채점 대상이 아니다. v0.2의 옛 이름(`lookup_notice`·`get_consultation_slots`·`prepare_*` 등)은 v0.5에서 없어졌다.

| ③ 도구 이름 | 계약표 4장 이름이 기준이고, 30문항 v0.5가 이름을 이미 맞췄다. 모델이 채우는 값은 v0.5에 맞추고 백엔드가 채우는 값을 따로 적었다(4.2, 11/18 강사 피드백 FB-001-1). 30문항 파일은 바꾸지 않는다 | 확정 (기본값 그대로) | 인혜·영민 |
| ④ 도구 실패 | 실패 코드는 태웅(T13)이 '다시 해볼 실패'와 '다시 해도 안 되는 실패'로 나눠 적는다(`retryable`). 실패 시 에이전트 행동은 영민(T14)이 4장 표에 채우고, 기본은 재시도 1번 → 그래도 실패하면 사람 카드다(11/18 영민 리뷰) | 확정 (기본값 그대로) | 영민 |
| ⑤ 카드 처리 기한(`due_at`, 설정값) | 민원 긴급·판단 필요 2시간, 민원 일반 24시간, 문의 4시간, 상담 요청 24시간, 알림장 당일 17:00. **주말·공휴일은 건너뛰고 센다**(금요일 18시 일반 민원 → 월요일 18시). 민원 긴급·판단 필요 2시간만 주말·공휴일에도 그대로 센다. 공휴일 목록은 설정값(위치는 인혜). 원장 보고(`director_report`)는 원래 민원 기한을 따름. 정보 요청(`needs_info`)·규칙 제안(`rule_proposal`) 카드는 기한 없음(지연 집계 제외). 원장 현황 '지연' = `due_at`이 지난 카드 | 확정 (B안: 주말·공휴일 제외) | 성주·지혜 |
| ⑥ 상담 시간 잡아 두기 | 학부모가 체크한 시간은 담임 확정까지 24시간 잡아 둔다. 지나면 풀고 담임에게 `slot_hold_expired` 알림 | 확정 (A안: 24시간) | 성주 |
| ⑦ 학부모 미확인 처리 완료(T04 F1) | 담임이 이유 글(`reason_text`, 예: '전화로 마무리함')을 남기면 학부모 확인 없이도 처리 완료할 수 있다. 이유가 없으면 409 `REASON_REQUIRED`(요청 상태를 보고 서버가 내는 오류라 형식 오류 422와 나눔)이고, DB 트리거도 거부한다(DB 설계서 9.1 F2-6). 원장 현황에 최근 30일 '학부모 미확인 완료' 수(`completed_unconfirmed`)를 따로 보여 준다 | 확정 (A안: 이유 남기면 완료) | 지혜·성주 |
| ⑧ 같은 질문 묶기 | MVP에서는 묶지 않고 요청마다 카드 한 장을 만든다. 나중에 더할 때(T04 5.2 [제안] "같은 질문 여러 건은 카드 한 장으로 묶고, 승인하면 모두에게 회신")는 일반 문의만, 같은 반 안에서만 묶고 민원과 아이 개인 정보가 들어간 질문은 뺀다(11/18 영민 리뷰) | 확정 (기본값 그대로) | 영민 |
| ⑨ 보류 재개 | `hold_until`이 되면 자동으로 `on_hold → awaiting_review`(받은함 '확인 필요')로 돌리고 담당에게 `hold_resumed` 알림. 자동 재개는 `approvals`가 아니라 `events`에 시스템 행위자로 남김 | 확정 (A안: 자동 재개 + 알림) | 성주 |
| ⑩ 요청 없는 카드(알림장 묶음·규칙 제안) | 받은함 '확인 필요'에 둠 | 확정 (기본값 그대로) | 성주 |
| ⑪ 역할별 생성 모델(설정값) | 감독·자료·기억·검사·코드 AI마다 환경변수 `LLM_MODEL_<역할>`(예: `LLM_MODEL_SUPERVISOR`)로 따로 바꿀 수 있게 둔다. 비워 두면 `LLM_MODEL_DEFAULT` = `gpt-6-luna`(D27). 역할별 교체는 다섯 에이전트 분리(T43) 뒤 앱 경유 평가에서 이득이 확인된 역할만, 팀 결정으로 한다 | 확정 (기본값 그대로) | 영민(T14)·인혜(`.env.example`) |
| ⑫ 모델 호출 사용량 기록 | 모델을 부를 때마다 `events`에 `action = llm_called`로 남기고 `detail`에 역할·모델 ID·입력/캐시/출력 토큰·걸린 시간을 넣는다(T19 마이그레이션 때 `action` 목록에 추가). 평가 실행(`eval_runs`)은 사용량 합계를 리포트에 같이 남긴다. 서비스 운영 비용을 추정하는 근거다 | 확정 (기본값 그대로) | 영민(T14)·태웅(T13·T19) |
| ⑬ 근무 시간 밖 긴급 알림(T04 F2, FR-21) | 근무 시간(평일 09~18시) 밖에 생긴 긴급 민원은 **아이 안전(`child_safety`)만 바로** 알리고, 교직원 비난·위협·법적 조치·개인정보 유출과 판단 필요 민원은 다음 근무 시작(09:00)에 보낸다. 서버가 `notifications.deliver_after`를 이 규칙으로 계산한다(T13). 기획서 FR-21 '아이 안전·발열만 바로'와 같은 방향 | 확정 (A안: 아이 안전만 바로) | 인혜(설정값)·지혜(T04 F2) |
