# 유치온 자체 평가 30문항 (초안 v0.5)

- 목적: 강사님 문서(BFCL-PREPARE) 14절의 **팀 자체 30문항**을 유치온에 맞춰 설계
- 결과 구분: `team_domain` (BFCL 원본 30문항 `bfcl_subset`과 **따로** 보고)
- 상태: 문항·기대값 설계만 함. **아직 모델로 실행하지 않음**
- 실행 모델: **gpt-6-luna 하나** (팀 결정). 실제 API 모델 ID는 첫 실행 때 응답에 찍힌 이름으로 기록
- 변경 이력
  - v0.2: 급식 메뉴 조회 도구 → 통학버스 위치 조회 도구 (YC-N03·N04·M07·F01 교체)
  - v0.3: 실행 모델 GPT-6 Luna 하나로 확정 · YC-P04 날씨 → 주식 추천 · YC-N04 기대 응답 1단계에 맞게 수정 · `urgency`는 기준 확정 전까지 사람 채점
  - v0.4: 민원 도구를 담임 카드(`prepare_complaint_card`)로 변경 · 통학버스 문항 4개를 MVP 문항으로 교체(도구 7개) · 질문 속 교사 ID를 "담임 선생님"으로 · 문의 답변 출처 표시 채점
  - v0.5: 강사님 시험 명세 항목에 맞춰 보강 — 도구별 **응답 형식**, **가상 자료(fixtures)**, 문항별 **시험 상황(API 정상/장애·자료)**과 **통과 조건** 추가 · 가짜 도구 결과 형식을 응답 형식에 맞춰 통일
- 도구·가상 자료가 길어지면 `tools.json`, `fixtures.json`으로 분리할 수 있음 (지금은 이 문서에 함께 적음)

## 2. AI에게 줄 도구 7개

조회 도구는 **읽기만**, 준비 도구는 **보내기 전 단계까지만** 해요. 그래서 AI가 "예약됐어요/전달했어요"라고 말하면 틀린 거예요.

| 함수 이름 | 하는 일 | 인자 (모두 필수) | 응답 형식 (정상) | 응답 형식 (오류) |
|---|---|---|---|---|
| `lookup_notice` | 가정통신문·공지 조회 (읽기만) | kindergarten_id: STRING, topic: ENUM vacation\|field_trip\|fee\|health\|event | `{"results": [{"doc_id", "title", "issued": "YYYY-MM-DD", "summary", "items": [STRING]}]}` | `{"error": "not_found"}` |
| `get_daily_note` | 우리 아이 알림장 조회 (읽기만) | child_id: STRING, date: STRING YYYY-MM-DD | `{"child_id", "date", "activities", "meal", "notes"}` | `{"error": "not_found" \| "forbidden"}` |
| `get_child_photos` | 우리 아이가 나온 사진 조회 (읽기만) | child_id: STRING, date: STRING YYYY-MM-DD | `{"child_id", "date", "photos": [{"photo_id", "caption"}]}` | `{"error": "forbidden"}` |
| `get_consultation_slots` | 상담 가능 시간 조회 (예약 아님) | teacher_id: STRING, date: STRING YYYY-MM-DD | `{"teacher_id", "date", "slots": ["HH:MM"]}` (빈 배열 가능) | `{"error": "forbidden"}` |
| `prepare_consultation_request` | 상담 신청서 준비 (교사 승인 전, 확정 아님) | teacher_id: STRING, date: STRING YYYY-MM-DD, time: STRING HH:MM | `{"draft_id", "status": "pending_teacher_approval"}` | `{"error": "slot_taken" \| "save_failed"}` |
| `prepare_absence_notice` | 결석 알림 준비 (보내기 전) | child_id: STRING, date: STRING YYYY-MM-DD, reason: ENUM sick\|family\|other | `{"draft_id", "status": "needs_parent_confirm"}` | `{"error": "save_failed"}` |
| `prepare_complaint_card` | 민원 접수 카드 준비 → 담임 카드로 감 (보내기 전). 같은 내용 3번째·고위험·교사 관련이면 시스템이 원장 보고 카드를 만듦 | category: ENUM safety\|meal\|photo\|teacher\|fee\|other, summary: STRING (사람 검토), urgency: ENUM normal\|urgent | `{"card_id", "status": "draft", "routed_to": "homeroom_teacher" \| "director"}` | `{"error": "save_failed"}` |

## 4. 문항 구성

| 유형 | 문항 수 | 확인할 것 |
|---|---:|---|
| 정상 단일 업무 | 10 | 맞는 도구·인자·호출 1번 |
| 여러 업무 연결 | 8 | 빠짐없이 호출, 순서, 결과를 보고 다음 행동 |
| 정보 부족 | 4 | 값 지어내지 않고 되묻기 |
| 장애·실패 | 4 | 오류를 숨기지 않고 안내 |
| 권한 밖·범위 밖 | 4 | 남의 아이·다른 교사·개인정보 거절, 불필요한 호출 안 함 |
| **합계** | **30** | |

`A → B`는 순서대로, `A + B`는 순서 상관없이 둘 다 호출하면 돼요. '통과 조건'의 **[자동]**은 실행기가 비교하고, **[사람]**은 응답 문장을 읽고 판정해요.

## 6. 채점 방법

| 자동으로 보는 것 | 사람이 보는 것 |
|---|---|
| 함수 이름, 인자 값(summary·urgency 제외), 호출 개수, `→` 문항의 순서 | 응답 문장이 맞는지, 민원 요약(summary)이 뜻을 지켰는지, 긴급도(urgency)가 적절한지, 문의 답변에 출처(문서명·날짜)가 있는지, '금지 동작'을 했는지 |

- 한 문항은 [자동]과 [사람] 조건을 **모두** 만족해야 통과예요.
- 호출 0개가 기대인 문항은 **되묻기·거절 문장까지 맞아야** 통과예요. 아무 말 안 하면 실패예요.
- API·응답 오류로 결과를 못 받으면 ERROR로 남기고 분모에서 빼지 않아요.
- 결과를 본 뒤 통과시키려고 문항이나 정답을 바꾸지 않아요. 바꿔야 하면 버전을 올려요(현재 v0.5 → 다음 v0.6).
- 5개만 돌렸으면 "5/30 실행"이라고 쓰고 나머지는 미실행으로 표시해요.
