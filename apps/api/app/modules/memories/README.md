# 개인 기억과 규칙

카드 거절·반려는 결정한 담임의 `rejection_reason` 기억으로 저장해요.
이유 코드·아이 이름을 가린 이유 글·출처 카드·당시 카드 판·결정 종류를 남겨요.
저장 전에 출처 카드 요청의 반 아이 이름을 `○○`로 가려요. 반이 없으면 같은 기관 전체를 봐요.
앞에 한글이 없고 뒤가 끝·공백·문장부호 또는 조사·호칭일 때만 가려요.
`하늘이가`·`마루랑`·`(하늘)`은 가리고, `하늘색`·`무엇이든`·`마루에서`·`올라온`은 남겨요.
조사·호칭과 원래 승인 기록은 그대로예요.
이유 글이 없으면 코드 이름을 남겨요. 원장의 결정은 담임 기억으로 학습하지 않아요.
목록·삭제는 기존처럼 본인 기억만 다루고, 삭제한 기억은 다음 제안의 횟수에서 빼요.
삭제할 때 본문과 structured도 비워요. 삭제 시각과 출처 연결은 이력용으로 남겨요.

같은 기관·사람·이유 코드의 지우지 않은 기억이 세 건 이상이면 `proposed` 규칙과
요청 없는 `rule_proposal` 카드를 만들어요. 제안 카드는 본인 받은함에 기한 없이 보여요.
기존 `proposed`·`active`가 있으면 그 ID를 돌려주고 새 카드·이력을 만들지 않아요.
거절한 규칙은 보관해요. 같은 주인·이유 코드의 마지막 decline 결정 뒤에 새로 쌓인
기억이 세 건 이상이어야 다시 제안해요. decline 전 기억은 다시 세지 않아요.
개인 규칙 카드는 다른 담임에게 재배정하지 않아요. 같은 반 다른 담임도 볼 수 없어요.
제안 알림은 주인에게 한 번 남겨요. 근무 시간 밖이면 다음 근무 시작에 보여요.

자동 대역은 코드별 안내 문장과 `{"reason_code": "…"}`만 저장해요.
자유 글에서 상담 시간이나 말투 규칙을 추측하지 않아요. `other`는 서로 같은 이유인지
알 수 없어 자동 제안하지 않아요. 입력한 글은 본인의 기억에만 남고 제안 문장에는 옮기지 않아요.
구체적인 규칙 추출은 기억 AI 몫이에요. `propose_rule` 입구로 `rule_text`·`rule_json`을
넘기면 같은 세 건 조건·중복 방지를 거쳐 저장해요. rule_json은 객체이고,
after·before가 있으면 HH:MM이어야 해요. 틀리면 VALIDATION_FAILED예요.
이 규칙 제안 입구는 실제 모델을 부르지 않아요.

DB 저장은 호출 쪽 트랜잭션을 써요. 같은 사람·이유의 기억 INSERT 전 자문 잠금으로
동시 세 번째 거절을 놓치지 않고, 기존 부분 유니크 제약으로 열린 규칙 하나를 지켜요.
규칙 결정도 같은 자문 잠금으로 기억 저장과 순서를 맞춰요.
규칙 제안만 savepoint로 묶고 저장 실패는 한 번 다시 해요. 그래도 실패하면 제안만
되돌리고 tool_failed 이력을 남겨요. 카드 거절과 거절 기억은 성공해요.
승인 기록·거절 기억 자체나 규칙 결정 저장의 실패는 그 결정 전체를 되돌려요.

규칙 결정 API는 로그인한 본인 소유만 허용해요. 남의 것·다른 기관·없는 것은 404예요.
연결 카드 → 규칙 순서로 잠그고 `proposed`에서만 `active`·`declined`로 바꿔요.
카드는 done·판 증가, approvals에는 approve·reject, events에는 approved·rejected를 남겨요.
같은 결정 재시도나 동시 결정의 패자는 기존 계약대로 409 `INVALID_TRANSITION`이에요.
규칙을 거절한 일 자체는 거절 기억을 다시 쌓지 않아요.

DB 상담 후보는 reason_code가 `slot_unavailable`이고 `active`인 규칙의 after·before만 적용해요.
제안 상태·거절 상태는 읽지 않아요. 자동 대역의 코드만 있는 규칙은 시간을 바꾸지 않아요.
mock 상담 후보는 기존 평일 15시·16시 중 확정 예약·살아 있는 체크와 겹치지 않는 칸을 골라요.
더 넓은 규칙 해석은 후속 작업이에요.

`reply_draft` 수정 승인은 커밋 뒤 FastAPI BackgroundTasks에서 원 초안과 실제 발송문을
비교해요. 초안을 덮어쓰기 전 복사하므로 승인 기록·공개 응답에 원문을 더 저장하지 않아요.
`LLM_MODEL_MEMORY`가 비면 모델 호출·저장 없이 끝나요. 켜면 `OpenAIModel("MEMORY")`가
후보 0~2개를 내고, 코드가 tone·80자·한 문장·아이 이름 가림·민감정보 형식·숫자를 검사해요.
같은 원·담임의 살아 있는 같은 문장은 건너뛰고, 12개를 넘으면 오래된 것부터 지워요.
structured에는 source=edit_approve와 승인 전 card_version을 남겨요. 실패는 별도 트랜잭션의
memory/tool_failed 한 줄로 남기고 이미 승인·발송한 결과에는 영향을 주지 않아요.
API 모드와 worker 모드 모두 이 작은 후처리는 API 백그라운드에서 해요. 메모리 후보를
만들기 위한 원 초안을 큐·추가 DB 칸에 복제하지 않기 위해서예요. API 강제 종료 때 유실될 수
있고 자동 재전달은 하지 않아요. 문의 두 작성 경로와 알림장은 본인 tone 최신 8개만 읽어요.
모의는 후보 저장·조회 계약만 흉내 내며 실제 기억 모델을 호출하지 않아요.

문의의 approve·edit_approve 뒤에는 같은 백그라운드에서 승인 답도 저장해요.
`EMBEDDING_MODEL=BAAI/bge-m3`와 임베딩 패키지가 있어야 하고, 꺼져 있거나 벡터를
만들지 못하면 저장하지 않아요. no_evidence·conflict·근거 없는 카드는 직접 쓴 답이라도
저장하지 않아요. saved_answer_sources는 조각 ID가 아닌 **문서 ID** 표이므로 카드 근거
조각의 문서를 중복 없이 연결해요. 질문은 원 아이 이름·민감정보 형식을 가리고, 답은
실제 발송문을 저장해요. created_at에는 해당 approvals의 시각을 써 approved_at으로 꺼내요.

검색은 같은 원·원 전체 또는 같은 반·active 답·같은 임베딩 모델/판만 대상으로 해요.
모든 근거 문서가 active·적재 완료·학부모 공개·적용 기간 안·해당 반 허용이어야 해요.
코사인 유사도 **0.80 이상 상위 1개**를 두 문의 작성 경로의 prior_answer로만 넘겨요.
실제 bge-m3 보정 자료가 없어 명세의 0.80을 유지해요. 새 질문의 chunks를 다시 검색·검사하며,
기억·prior_answer는 검사 AI 입력이나 card_evidence에 넣지 않아요. 문서가 바뀌면 0001의
기존 documents_invalidate_saved_answers 트리거가 off 답까지 invalidated로 바꿔요.
기간·공개 범위는 꺼낼 때도 다시 확인해요. 새 트리거·마이그레이션은 없어요.
모의 승인 답은 모델 없이 고정 가짜 벡터로 저장만 흉내 내요. 모의 검색 도우미는 시험에서
받은 벡터로 같은 범위·문서 조건을 확인하며, 질문의 실제 의미를 판정하지 않아요.
